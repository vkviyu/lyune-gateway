# Lyune 帧协议设计

## 文档定位

这是 Lyune 帧协议的**唯一权威描述**，同时记录格式背后的取舍理由。原
`docs/protocol.md`（旧协议）已删除——不保留两份并存的协议描述。

第一步（§11）已落地：`src/protocol/frame.zig`、`codec.zig`、`framing.zig` 与
`src/worker/ingress.zig` 实现的就是本文档 §4、§5.1（`.gateway` / `.service` 部分）、
§7.1、§7.5。`.peer` / `.multicast`（含流式，§5.3）与 datagram（§6）也已实现，
落点见 §11 的第二、三步。

**目标定位有两层**：自用的 IM / 大文件 / AI 流式 / 文档协作 / 多人游戏网关，以及
对外的 **IM SaaS**——第三方接入方使用本网关 + 官方 SDK，鉴权由接入方自己的服务端完成。
后者不改线格式，但改了命名空间、配额和证书运维的语义，见 §12。当前代码已经实现
realm 隔离、配额和网关侧后端客户端证书能力，但还没有完成生产配置强制与真实多 realm
部署验证；当前状态统一见 `docs/status.md`。

重写的前提是当前没有任何外部使用者，因此**不考虑线格式兼容**。

## 1. 设计原则

### 1.1 不重复 QUIC 已经提供的能力

旧协议里有若干字段在做 QUIC 已经做好的事：

- **多路复用** —— QUIC stream id 就是多路复用键，帧里不需要再放通道号
- **请求/响应关联** —— 双向流天然关联：在哪条流上发的，响应回到那条流
- **流内有序** —— QUIC 保证，不需要序号
- **流控** —— QUIC 的连接级与流级流控已经存在，协议不再自定义窗口

因此旧协议的 `seq`（4 字节，全代码库无人读取）和 `flags.need_ack`（未使用）直接删除。

### 1.2 校验成本花在不受信任的方向

- **上行（客户端 → 网关）**：客户端是攻击面。逐帧解析、逐帧选路、逐帧过门禁；
  分帧违规立即 RESET_STREAM，不做重同步。
- **下行（后端 → 网关 → 客户端）**：后端由配置指定且经过双向认证，是受信任方。
  网关按流转发字节，不解析。这条正当性**依赖 mTLS**（见 §10.1），
  在 mTLS 落地之前下行的信任假设是不成立的。

### 1.3 客户端只说"什么"，不说"怎么"

客户端给出目的地（`dest_kind` + 标识），网关按服务端配置决定用哪条传输路径
（direct / relay）。同一个目的地从直连切到中继，客户端零改动。

### 1.4 热路径以零拷贝和有界分配为目标

帧解析在 QUIC 的接收缓冲上就地进行，解出的帧是借用而非拷贝；只有跨回调的
残帧才需要缓冲，且最多一帧。转发给后端与写回客户端通常复用原始字节，不重新编码。
连接槽位和主要交接/接收池在启动期定容，但 exchange、spill、inflight 等状态仍使用动态
容器，因此当前实现不能笼统宣称“运行期零分配”；真实资源上界与剩余工作见 `status.md`。

### 1.5 语法对称，权限不对称

同一套帧格式两个方向都用，方向由"谁发出"隐含。但**权限必须不对称**：
客户端只能寻址 `.gateway` 和 `.service`；`.peer` / `.multicast` 只对后端开放。
否则客户端可以绕过业务层直接骚扰任意用户。

## 2. 与旧协议的差异

| 删除                        | 理由                                                                |
| --------------------------- | ------------------------------------------------------------------- |
| `magic`（2B）               | ALPN 在握手层已保证协议一致；分帧违规杀流不重同步，magic 无用武之地 |
| `version`（1B）             | 版本是连接级属性，移入 ALPN 字符串                                  |
| `seq`（4B）                 | 请求关联由 QUIC 流提供；应用级去重是业务层的事                      |
| `flags.need_ack`            | 未使用；ACK 语义属于 QUIC 或业务层                                  |
| `TransportMode`             | buffered / streaming 的区别被"一次交换有几帧"取代，见 §5.2          |
| 每帧重复`group + route_key` | 路由是流级属性，只在流的第一帧声明                                  |

新增：`dest_kind`（目的地类型）、`frame_type`（OPEN / DATA / DATAGRAM）。

帧头从固定 16 字节变成：**首帧 8 字节，后续帧 4 字节，datagram 2 字节**。

---

## 3. 连接层

- **ALPN 承载版本**：`lyune/1`。版本不匹配在 QUIC 握手阶段就失败，不进入帧层。
- **一个客户端一条 QUIC 连接**。所有逻辑交换复用这条连接上的多条流。
- 单帧上限 **64 KB**（`body_len` 为 u16）。超过的内容由发送方切成多帧。

64 KB 这个数字是有意选的：它让重组缓冲可以做成定容池（16 MB 的旧上限无法预留），
是走向"启动期一次分配、运行期零分配"的前置条件。

## 4. 流帧格式

### 4.1 OPEN —— 一次交换的第一帧（8 字节）

```
偏移  长度  字段
0     1     frame_type = OPEN
1     1     flags
2     2     body_len (u16, 大端)
4     1     dest_kind
5     1     reserved（必须为 0，解码时校验）
6     1     group
7     1     route_key
```

`group + route_key` 仅在 `dest_kind = .service` 与 `.gateway` 时有意义。

### 4.2 DATA —— 同一次交换的后续帧（4 字节）

```
偏移  长度  字段
0     1     frame_type = DATA
1     1     flags
2     2     body_len (u16, 大端)
```

目的地不重复声明——它是流级属性，由 OPEN 定型。后续帧即使伪造也无法改变投递目标。

### 4.3 flags

```
bit 0  eof         本次交换的最后一帧
bit 1  report      请求投递回报（仅 OPEN 有意义，见 §5.5）
bit 2  unreliable  投给成员时改走不可靠通路（仅 `.multicast` 的 OPEN 有意义，见 §6.3）
bit 3-7            保留（必须为 0，解码时校验）
```

`sof` 不再需要：OPEN 本身就是起点。旧协议里"首帧必须带 sof"那条校验随之消失。

### 4.4 一条 QUIC 流 = 一次交换

- 流的第一帧必须是 OPEN
- 后续帧必须是 DATA
- 带 `eof` 的帧是最后一帧；之后该流上不应再有帧
- QUIC 的 FIN 与 `eof` 语义重叠时以先到者为准，网关据此收尾后端流

网关按流维护一条交换记录，条目的存在就是"这条流上有一次已被接纳的交换"。
它在 QUIC FIN 或流被终止时清理，也是上面第三条与"一条流不得有两个 OPEN"
两条规则的判据（分级见 §7.5）。

被拒绝的交换**不留记录**：网关回了错误帧就当这次交换没发生。这条选择的理由
在 §7.5 末尾。

## 5. 目的地模型

### 5.1 四种目的地

```
dest_kind:
  0  gateway     —— 网关自己
  1  service     —— 后端服务
  2  peer        —— 另一个客户端
  3  multicast   —— 一组客户端
```

未知取值一律拒绝（白名单解码），这样将来扩展时旧网关会明确报错而不是误投递。

**`.gateway`** —— 与网关本身的交换。`group + route_key` 用作控制类型，
沿用现有 `ControlType` 的取值划分：心跳类 `0x00-0x0F`、认证类 `0x10-0x1F`、
连接控制类 `0x20-0x2F`。通道绑定（§6）也在这个空间里新增取值。

与网关的交换**不受"必须单帧"限制**，同样可以是 OPEN + DATA×N 的流式形态，
两个方向都可以。旧协议做不到这一点：那里 `TransportMode` 把"和谁交互"（`control`）
与"怎么传输"（`buffered` / `streaming`）挤进了同一个字段，于是控制帧只能一次性，
数据帧也无法指向网关。新设计把两个维度拆开——`dest_kind` 回答"和谁"，
帧数回答"怎么传"。

因此下列交互成为可能：客户端向网关流式上报遥测；网关向客户端持续推送连接质量
报告或限流通知序列。**第一步实现里这条路还没打通**：`.gateway` 的 OPEN 必须带
`eof`，不带的会收到一个业务级错误帧（"streaming control exchange not supported"）。
线格式已经允许，缺的是消费方。

控制类型是白名单，不在白名单内的取值一律拒绝。特别地，**修改网关配置或路由表
不属于数据面**，不进入这个白名单——那是运维面的事。

**`.service`** —— `(group, route_key)` 查 `BackendTransport`。这是**配置规模**的
命名空间（等于"系统里有多少个后端 handler"，几百量级），65536 足够；
所有节点加载同一份配置，因此不存在跨节点冲突。

多 realm 下这个命名空间必须按 realm 隔离（键变成 `(realm, group, route_key)`），
否则不同接入方的 `(1,0)` 会撞在一起，见 §12.2。

**`.peer`** —— 目标是一个或多个具体客户端。body 前缀是目标列表：
`count (u16) + dest_id[count] (每个 8 字节)`。网关按 `dest_id` 投递：落在本节点的直接
写回，落在其他节点的走跨节点投递（问题来源见 §8.4，解法分层见 §8.5）。

支持批量是为了让后端的扇出成本保持 O(1)：一个 500 人群，后端发一帧带 500 个
`dest_id`，而不是发 500 帧。单帧上限 64 KB 决定了每帧最多约 8000 个目标
（`(65536 - 8 - 2 - 负载长度) / 8`），更大的群分多帧发。

**`.multicast`** —— 目标是一个或多个组播组，成员表在网关，扇出由网关完成。
body 前缀**与 `.peer` 完全同形**：`count (u16) + group_id[count] (每个 8 字节)`。

同形不是巧合而是有意收敛：两条路径的编解码、截断校验、投递回报因此完全一致，
"一帧发给多个组"也免费得到支持。原设计写的"8 字节组标识"只是它 `count = 1` 的特例。

成员关系由**后端**通过下行控制交换 `join_group` / `leave_group` 维护（§7.2），
网关自己没有任何判据——谁能进哪个协作文档、哪局游戏、哪个直播间是业务判断。
网关只持有"组 → 连接"这份投递索引，不持有"谁有权进组"这份业务状态（§12.1）。

`.peer` 与 `.multicast` 的分工见 §8：前者成员由后端逐次随帧给出、网关无状态，
跨位置成本 O(目标数)；后者成员表在网关，跨位置成本 O(位置数)、**与组成员数无关**。
**IM 群聊用批量 `.peer`，不用 `.multicast`。**

命名说明：`.multicast` 是应用层组播，与 IP 组播（IGMP）无关。选它而不是 `.room`
是因为群聊、文档协作、游戏房间、直播弹幕都是组播，`.room` 只贴合其中两个。

### 5.2 buffered / streaming 的消失

旧协议用 `mode` 区分"一帧一请求"和"多帧一请求"。新设计下这个区别是自然的：

- **一次性交换** = OPEN 直接带 `eof`
- **流式交换** = OPEN + N × DATA + 最后一帧带 `eof`

网关的行为统一成三条规则，不再有模式分支：

- OPEN → 开一条后端流（或按 `.peer` / `.multicast` 投递）
- DATA → 往同一条追加
- `eof` → fin

旧协议里"一帧一请求"和"多帧一请求"是两条几乎平行的转发路径；新协议下它们合并成
一条，区别只在开后端流时是否顺带 fin。

### 5.3 dest_id 读取但不剥离

`.peer` / `.multicast` 的目标列表占 body 前缀，**只出现在 OPEN 帧上**——目标是流级
属性，与 `dest_kind` 一样不在后续 DATA 上重复。网关读它来决定投递目标，
但**不从 body 里摘掉**，整帧原样转发给接收方，接收方按同样规则跳过这段前缀。

理由是零拷贝：剥离前缀会改变 `body_len`，网关就必须为每个目标重新编码帧头并拷贝一次。

代价是接收方能看到同批次其他目标的 `dest_id`。对群聊这通常无害（群成员本来互相可见），
但**如果某个场景要求接收方之间互不可见，就必须由后端拆成多帧单目标发送**，
不能靠网关剥离。

#### 流式推送：会话身份就是它所在的那条流

一次性推送（OPEN 带 `eof`）与流式推送（OPEN + DATA×N）的区别只有一个：**后续 DATA 帧上
没有目标列表**（前缀只在 OPEN 上，见上文），所以网关必须记住"这条流的目标是谁、我给
每个目标开的是哪条客户端流"。难点全在"记在哪、怎么跨位置对上号"。

**结论：不在线格式里加任何字段。每一跳都用它所在的那条流来标识会话。**

| 这一跳                   | 会话身份                                       |
| ------------------------ | ---------------------------------------------- |
| 后端 → 网关              | 后端那条 QUIC 流（`inflight.StreamKey`，已有） |
| 网关 → 同机另一个 Worker | 交接信封的 `AppMessage.session`（不进帧）      |
| 网关 → 另一个节点        | 对等链路上一条专属 QUIC 流                     |
| 网关 → 客户端            | 该连接上一条专属推送流                         |

四条选择的依据各不相同，值得逐条说：

- **同机跨 Worker 用信封而不是帧**，与 `realm` 完全同一个理由（§12.3）：会话号是网关内部
  的记账，让目标 Worker 从帧里读它就等于把内部状态暴露成协议字段，而后端可以伪造它。
- **跨节点用一条专属流**，因为对等链路本来就是 QUIC：一条流天然就是一个会话，接收节点
  看到的形态与后端直连时完全一样（OPEN 然后 DATA），`openPeerNodeExchange` 不需要认识
  "会话"这个概念。**帧头里没有 8 字节可用**（只有一个保留字节，realm 提示已经占了两个），
  所以想在跨节点这一跳塞会话号本来也塞不进去——这个约束反过来指向了正确答案。
- **客户端侧一条专属推送流**，因为客户端要能重组：同一会话的分片必须按序到达同一条流，
  这和 `.service` 的响应形态一致，客户端不需要为推送再学一套规则。
- **每 Worker 一张很小的会话表**（会话号 → 冻结下来的目标集合），而**不是**每连接一张。
  每连接一张表解决不了"发起方还得知道会话里有哪些连接"这份状态，而发起方一旦要存连接，
  存的就必须是带 generation 的 `ConnToken`——连接中途断开、槽位被新连接复用时它必定失配，
  那个目标自然掉出会话；存原始句柄则是把这一帧写进**另一个用户**的连接。所以一张表就够，
  形状仍然与 §6.1 的通道表同构：MQTT 5 的 topic alias 也是"绑定一次，之后只带一个短句柄"。

**成员集合在 OPEN 时冻结。** 会话中途新连上来的设备**不**接这条流——它没收到头部，
把尾巴发给它就是一段残缺的字节流。它应当走后端的离线补偿路径。

**投递回报在 OPEN 那一刻就结算完**：可达性此刻已经定了（成员集合已冻结），而后续 DATA
上没有目标列表，再也没有第二次结算的机会。

**异常结束用 RESET_STREAM，不是 fin。** fin 的含义是"完整结束"，客户端会把半个文件当成
整个文件收下，而它没有任何方式发现自己被截断了。后端把推送流关了却从没发过 eof、会话
静默超时、目标列表不合法——三种情形都作废下游的每一条流。同机其他 Worker 收不到
RESET（它们持有自己的会话），所以给它们发一条**空载荷**的交接消息当作废信号；应用帧
最短也有 4 字节帧头，所以 0 字节这个取值不会与真实帧混淆。

**目标数有两道上限。** 第一道是一帧 OPEN 里的目标数（`max_list_targets`，个位数）：
列表是后端编的，它**能控制**，所以超限直接拒掉整个会话——截断成前 N 个会让后端以为全都
发出去了。第二道是一个位置上的连接数（`max_local_targets`）：一个 `dest_id` 可以对应多条
连接（多设备，§5.6），这个放大网关只能被动接受，因此上限更宽，超了就停在上限处并记 warn。

两道上限的理由是同一个：**在网关里把一条流复制 N 份，出口带宽就乘以 N**。个位数以上的
流式扇出是架构选错了位置——那种需求应该由后端推给广播层，而不是让网关做扇出。一次性
推送不受这条限制（它只有一帧）。跨节点同理有 `max_nodes`。

真实场景也支持这个取舍：流式推送的用例是"给某台设备下发大文件 / 一路 AI 流"，目标通常
是一个 `dest_id`；而群聊、文档协作是多目标小消息，一次性推送足够。

`.multicast` 与 `.peer` 走**完全同一条会话路径**，区别只是目标条目是组标识而不是
`dest_id`：冻结成员集合、按会话续传这两件事一模一样，所以两者不需要各写一遍。

### 5.4 权限矩阵

| 发送方 | 允许的 dest_kind                                                            |
| ------ | --------------------------------------------------------------------------- |
| 客户端 | `.gateway`、`.service`                                                      |
| 后端   | `.peer`、`.multicast`、`.gateway`（仅 kick_off / join_group / leave_group） |
| 网关   | `.gateway`（如 kick_off、redirect）                                         |

客户端发出 `.peer` / `.multicast` 一律拒绝并终止该流。
例外：客户端可以在通过 `.gateway` 的 `bind_channel` 绑定通道之后，经该通道向那个
`.multicast` 组发不可靠数据（见 §6）。这不是权限漏洞——绑定的判据是**这条连接已经是
该组的成员**，而成员关系只能由后端的 `join_group` 建立，所以"能发给这个组"这件事的
权威仍然在后端。`.peer` 不在例外之内：网关对"这个客户端能不能不可靠地寻址那个账号"
没有任何本地依据（§6.1）。

后端方向的 `.gateway` 是**封闭白名单**，不是"全部控制类型"。原先这一格写的"全部四种
dest_kind"与 §7.2 的实现自相矛盾，已修正：后端寻址 `.service` 无意义（网关不是后端的
客户端），而它能对网关下的指令必须逐条列举——否则将来给客户端方向新增一个控制类型，
就顺带把它变成了后端的一项权限。

#### 为什么禁止客户端的可靠广播

客户端要向多个客户端可靠广播，表达方式是两跳：

```
客户端 --OPEN(.service)--> 网关 --> 后端
后端   --OPEN(.peer 批量 / .multicast)--> 网关 --> N 个客户端
```

多这一跳不是妥协，是必需的。需要广播的场景里三个都要求有权威：

- **IM 群聊**：要落库、过反垃圾、触发离线推送、同步多端。客户端直接广播会绕过全部业务逻辑。
- **文档协作**：op 必须由服务端定序（OT）或至少持久化快照（CRDT）。客户端各自广播会让
  不同客户端收到的 op 顺序不一致，收敛失败。这是**正确性**问题，不是安全问题。
- **游戏关键事件**：需要权威服务端校验，否则等于给外挂开门。

唯一有损失的是"既要可靠、又不需要校验"的场景（如游戏内聊天），它多付一个
网关↔后端的内网 RTT（通常远小于 1 ms），换来校验与审计能力。

而真正延迟敏感、真正不需要逐包校验的高频状态同步已经由 datagram 通道覆盖，
那条路径本来就不经后端。所以延迟敏感的需求没有被牺牲。

一句话概括这条界限：**可靠广播必须有权威（要么定序、要么校验），不可靠广播不需要。**

### 5.5 投递语义

网关的投递是 **at-most-once**，不是 at-least-once：

- 扇出后不保证对方收到——连接可能正在断开、QUIC 流可能被重置、进程可能在写入后崩溃
- 网关不做任何存储，因此做不到"必达"

IM 要的消息必达必须靠**客户端 ACK + 后端重试**，那是业务层的能力。
更准确地说：**网关解决"在线投递"，不解决"消息系统"。** 离线存储、上线补拉、
多端已读游标全部在后端。这个边界是有意的——不做存储才能保持无状态横向扩展。

#### 投递回报

后端需要知道哪些目标投不出去，才能触发离线存储。既然 `.peer` / `.multicast` 是后端
在自己开的双向流上发出的，网关就在**同一条流上回写投递回报**：不可达的
`dest_id` 列表（`count (u16) + dest_id[count]`）。

回报是**按需**的，由 OPEN 的 `flags.report` 位请求。游戏状态广播这类不关心
投递结果的场景不置位，省掉回程带宽。

"不可达"的判据是**该 `dest_id` 一条活连接都没有**（见 §5.6 的多重性决议）。
有一条写成功就不算不可达——后端要的信号是"该不该转离线存储"，而不是
"多端里有几端收到了"，后者属于业务层的已读游标。

#### 跨位置之后回报的准确含义

`dest_id → [connection]` 索引是每 Worker 一份的，所以目标可能根本不在收到推送的那个
位置上。此时回报的含义收窄为**「本位置是否受理」而不是「是否已投递」**：

- 目标的 home 就是本 Worker → 回报是准确的（"一条活连接都没有"）
- 目标的 home 在别处 → 转投成功即算可达，转投失败才回报不可达

为跨位置这一跳单独加 ack 并不能让端到端可靠——客户端那一跳照样会丢，只是把不可靠
往后推一格。真正要"消息必达"仍然必须靠后端离线存储 + 客户端拉取。

**这条也是选路策略影响可观测性的地方**：亲和模式下 home 唯一，回报仍然可用；
广播模式下发起方无从知道有没有别的位置命中，`unreachable` 退化成"本位置没有"，
后端会为在线用户白转一次离线存储。这是默认选亲和的第二个理由（第一个见 §8.5）。

`.multicast` 的回报天生只能表达"本位置一个成员都没有"——组成员分布在各位置，
而这正是它省下 O(成员数) 的代价。

### 5.6 dest_id 的多重性

**一个 `dest_id` 可以解析到 N 条连接。** 索引的值是连接列表，不是单条连接。

这条选择的关键理由不是"多端方便"，而是 **presence 的归属**："这个标识现在有哪几条
连接在线"本来就是网关的知识。若一个 id 只对一条连接，后端就必须自己枚举每台设备的
id，等于维护一份网关状态的副本，而且必然和网关的真实状态存在竞态窗口。

附带收益有两条：500 人群人均 2.3 端时，帧里的目标数从 ~1150 降回 500；投递回报的
含义也变得可直接使用（见 §5.5）。

`dest_id` 对网关是**完全不透明的 8 字节键**，网关不知道它代表账号、设备还是机器人。
因此"只发给某台设备"不是被牺牲，而是同一机制的扩展：一条连接可以注册在多个
`dest_id` 下（账号级一个、设备级一个），索引本来就按 `dest_id` 建，加这个不改线格式、
不改索引结构。第二步只落"一个 id 对多条连接"，"一条连接多个 id" 等有真实需求再加。

多 realm 下这个键必须带 realm（`(realm, dest_id)`），否则不同接入方分配的同一个数值会
互相寻址到——那是跨 realm 消息泄露，见 §12.2。

两条必须一起成立的约束：

- **`dest_id` 只能由认证服务下发**，绝不能取自客户端声明的字段（格式见 §10.3）。
  否则任何人都能把自己注册成别人的 id，然后收走别人的消息。
- **跨连接没有顺序保证。** 同一个 `dest_id` 的 N 条连接是 N 次独立写入。IM 多端各自
  靠后端给的序号收敛，文档协作的 op 顺序按 §5.4 本来就必须由后端定序，两者都不依赖
  网关的写入顺序。但不要假设"网关按顺序投递"。

## 6. 不可靠通路（datagram）

面向多人游戏的状态同步。可靠有序流会因队头阻塞产生延迟尖刺：丢一个包，
后面已到达的状态也得等重传。QUIC DATAGRAM（RFC 9221）没有这个问题。

### 6.1 通道绑定

datagram 没有流，无法用 OPEN 声明目的地。若每个 datagram 自带 8 字节 `dest_id`，
20 字节的状态包要付 12 字节头（37%）。改用**先绑定、后发送**：

1. 客户端在可靠流上发一个 `.gateway` 交换（`bind_channel`）：把通道 N 绑到某个组播组
2. 网关校验授权（一次），在该连接上记下 `channel → group_id`
3. 之后 datagram 只带通道号

每连接一张很小的通道表（8 槽，定长数组内联在连接上下文里）。**授权从每包检查收敛为
绑定时一次**，热路径上因此没有授权查找。

**授权判据是「这条连接已经是该组的成员」。** 而成员关系只能由后端的 `join_group`
建立（§7.2），所以这是一次有权威来源的本地判断，不是采信客户端的自述。

**只能绑到组播组，不能绑到 `dest_id`。** 本节早先的版本两种都列了，但 `.peer` 那半边
过不了 §5.4 的权限矩阵：网关对"这个客户端能不能不可靠地寻址那个账号"没有任何本地
依据，临时发明一个就正好是 §5.4 要防的越权——绕过后端的反垃圾与定序直接骚扰他人。
需要 1:1 不可靠通路时，让后端把两条连接放进一个两人组：组成员边本来就是池化的，
这不额外花钱，授权也留在了它该在的地方。

**通道号由客户端自选**（它是这条连接上的本地资源，与流号同理），所以绑定成功不需要
网关回传任何编号；成功的回执就是把 `bind_channel` 原样回一遍，失败走 `gateway_error`。

**吊销准入必须连通道一起收走。** 这是"热路径不查授权"的代价：`kick_off` 在清掉
`authenticated` 的同一处清空通道表，否则一条被踢、还没断开的连接仍能往组里灌状态包。
另有一道兜底——上行路径上仍会判一次 `isAdmitted`，它不是授权查找而是"这条连接此刻
还算不算在线"，两次加载加一次比较，用来盖住 token 自然过期这条无人主动通知的路径。

### 6.2 datagram 格式（2 字节）

```
偏移  长度  字段
0     1     frame_type = DATAGRAM
1     1     channel
```

不需要 `body_len`——QUIC 直接给出 datagram 长度。不需要分帧——每个 datagram
本身就是完整单元，不会跨回调被切开，因此不经过残帧重组路径。

20 字节负载的开销从旧协议的 16 字节（44%）降到 2 字节（9%）。

保留 `frame_type` 而不是直接用 1 字节通道号，是为了让 datagram 与流帧共享同一个类型
空间：将来要在不可靠通路上加第二种形态（例如带序号的状态帧），判据仍然是第一个字节。

**尺寸上限来自传输参数**（RFC 9221 的 `max_datagram_frame_size`，配置项同名）。
DATAGRAM **不分片**：超限的包发不出去，也不会被切开——切开就需要分片 id、乱序重组、
超时回收，等于在不可靠通路上把流重新实现一遍。默认 1200 落在 IPv6 最小 MTU（1280）
扣掉各层包头后的安全区里，所以满载 datagram 不会触发 IP 分片。

**它默认只在面向客户端的监听器上开启。** 网关↔后端、网关↔对等节点这两条链路都只说
可靠流，代码里的默认值因此是 0（关闭）——给它们默认打开等于凭空多出两条谁都不该走、
也没人测过的路径。

### 6.3 扇出：一个标志位复用整套可靠选路

组成员散落在本位置、同机其他 Worker、其他节点上（成员的落点由各自的 `dest_id` 决定，
与 `group_id` 无关，§8）。所以不可靠投递面对的是与 `.multicast` **完全相同**的选路问题。

答案是不新写一条路：把负载装进一个带 `unreliable` 标志（flags bit 2）的单目标
`.multicast` OPEN 帧，然后交给 §8.5 那套已有的扇出。标志位跟着帧走，于是

- 本位置：投给绑过通道的成员，形态是 datagram
- 同机跨 Worker：交接队列，目标 Worker 读到标志位后同样落成 datagram
- 跨节点：对等链路上的普通 `.multicast` 帧，收方节点在本地落成 datagram

三条路一个字节都不用改。代价是一次 ≤ `max_datagram_frame_size` 的 memcpy；换来的是
不必维护两份必须同步演化的选路不变量，而后者才是真正贵的东西。

顺带地，**后端也能用这个标志**推不可靠组播（游戏世界状态），语法与客户端上行完全对称。

**跨节点那一跳是可靠有序的**，这是有意的：丢包发生在最后一公里，不在机架内部。用机架
内的可靠链路换来零新增线格式、零新增配置、零新增回调路径。

**只投给绑过通道的成员。** 绑定既是授权，也是"我要不可靠投递"这个意愿的表达。没绑的
成员被跳过，而**不是**降级成可靠推送——降级会让 60Hz 的状态流在那条连接上堆成队头
阻塞，正是这条通路存在理由的反面。

**可观测性靠计数器，不靠日志。** 逐包路径上记日志会在 60Hz × N 个玩家下把磁盘写满，
但丢弃必须可见（否则表现成"某些玩家偶发卡顿"），所以每个 Worker 各持一对
`datagrams_in` / `datagrams_dropped`。

## 7. 网关行为

### 7.1 上行

```
QUIC 流数据回调
  → 就地逐帧扫描（跨回调残帧进 spill，最多一帧）
  → 按 frame_type 与 dest_kind 分派
      .gateway   → 本地处理（心跳/ping/认证/绑定通道/断开）
      .service   → OPEN 开后端流并登记回程映射；DATA 追加；eof fin
      .peer      → 拒绝（客户端无权）
      .multicast → 拒绝（客户端无权）

QUIC datagram 回调
  → 解 2 字节头 → 查该连接的通道表 → 按组扇出（§6.3）
  → 任何一步不成立都是"丢这一包 + 计数"，绝不关连接
```

协议违规不尝试恢复，直接关闭整条连接；业务失败在流上回错误帧。分级见 §7.5。

### 7.2 下行

```
后端接收轮询
  → 按归属分派（判据全部是网关自己的表，不是帧内容）
      在认证等待表里 → 累积到 fin，解析准入结果（§10.3）
      在回程映射里   → 原样字节写回客户端流，不解析
      在流式会话表里 → 沿会话续传给冻结下来的每个目标（§5.3）
      后端主动开的流 → 分帧，按 dest_kind 分派：
                         .peer      → 按目标列表扇出（本位置 + 转投）
                         .multicast → 按组成员表扇出（本位置 + 转投给所有位置）
                         .gateway   → 后端 → 网关控制交换（白名单，见下）
                         .service   → 拒绝：网关不是后端的客户端
                       OPEN 不带 eof 则开一个流式会话，冻结成员集合
                       按需回写投递回报
      以上都不是     → 孤儿响应（客户端早已断开、条目已回收），丢弃
```

分派顺序不能反过来由帧内容决定，否则后端可以把一个数据响应伪装成认证成功。

**"后端主动开的流"与"孤儿响应"都查不到回程映射，靠传输层的 `peer_initiated`
区分**（网关是后端连接上的 QUIC 客户端，因此 `stream_id` 的最低位就是"谁开的"）。
不区分的话，客户端断开高峰期的孤儿响应会被当成畸形推送刷日志，而真正的推送会被
当成孤儿静默丢弃。

推送这条路是 §1.2"下行不解析"的例外，但例外的判据仍然是网关自己的表（这条流是
后端开的），而不是帧里的某个字段。要解析是因为投递目标写在 body 前缀里。

**错误处理与上行不同**：上行的编码违规会关掉整条客户端连接，下行不能——一条后端
连接承载着所有客户端的请求，为一个畸形推送杀掉它等于让全体在途请求一起失败。
因此下行一律"记日志 + 丢弃这条推送流"。

#### 后端 → 网关的控制交换

这是 `.gateway` 在下行方向唯一被允许的用途：**后端请求网关对某些连接执行一个动作。**
它与"网关不是后端的客户端"不矛盾——后端不是在借隧道调别的服务，而是在指挥网关自己。
语法与客户端方向完全相同（`.gateway` + `route_key = ControlType`），**但白名单不同**，
这正是 §1.5「语法对称，权限不对称」。

| 控制类型                     | body                               | 作用                 |
| ---------------------------- | ---------------------------------- | -------------------- |
| `kick_off`                   | `TargetList` of `conn_token`       | 断开指定的那几条连接 |
| `join_group` / `leave_group` | `group_id` + `TargetList` of token | 维护组播组成员       |

三者都按 **`conn_token`** 而不是 `dest_id` 定位，理由相同：`dest_id` 是一对多的（§5.6），
而"换设备登录只踢旧设备"、"这台设备打开了这个文档"都必须精确到一条连接。后端在认证时
就拿到了 `conn_token`（§10.3 的 `AuthContext`），本来就要为 kick 存着它。

`conn_token` **自带位置**（`node_id | worker_id | slot | generation`），所以这三种指令的
寻址是精确的：既不需要算 home，也不需要广播。这是 §8.4「两跳都不知道」的破解口——
它们的前提是连接**已经认证过**，那一刻网关完全知道"我在哪"，只要说出来就行。
CID 不能事后重贴，token 可以。

两条必须一起成立的约束：

- **realm 只能取自发来这条指令的 transport 的注册表键**，绝不能从 body 里读。否则
  realm A 的后端拿一个猜中的 token 就能踢掉 realm B 的用户、或把它塞进自己的组
  （后者更糟：它能因此收走那个组的全部广播）。
- **这条通道的安全性完全依赖网关 ↔ 后端的双向认证（§10.1 的 mTLS）。** 在 mTLS 落地
  之前，任何能连上后端端口的东西都能冒充后端。

### 7.3 下行的形态由后端决定

后端写几次、什么时候带 `eof`，客户端就那样收到。网关不合并也不拆分。
因此四种组合都合法：一次性请求 + 流式响应（AI 逐 token）、流式请求 + 一次性响应
（上传后回 ack）、以及另外两种。

### 7.4 网关主动发起的交换

`kick_off`、`redirect`（§8.5 策略 B）、以及向客户端的推送，都需要**网关主动开一条
QUIC 流**并在上面发 OPEN（`dest_kind = .gateway`）。

这是对客户端实现的一条硬要求：**客户端必须能接收服务端发起的流。** QUIC 本身支持
server-initiated stream，但客户端 SDK 得处理这类流，而不是只在自己开的流上读。

旧协议下网关从不主动开流——所有下行都写在客户端开的那条流上，因此不需要这个能力。
新设计把它变成必需项，客户端 SDK 的最低要求随之提高。

**关闭连接时的帧与错误码是一对，不是二选一。** `kick_off` / `redirect` 都是"发一帧，
然后关连接"，而那一帧可能在关闭竞态里送不到。因此每种都配一个 `AppError`
（`kicked = 0x02`、`redirected = 0x03`），它一定随 CONNECTION_CLOSE 到达。
客户端靠错误码区分该做什么：`kicked` 是"该重新认证"，`redirected` 是"换地址重连，
凭据还有效"。合成一个会让 SDK 在被重定向之后白走一遍认证失败路径。

### 7.5 错误处理分级

分两级，判据是"字节流本身还可信吗"。

**连接级 —— 关闭整条连接（`picoquic_close` 带 application error code）**

- 未知 `frame_type` 或 `dest_kind`
- 保留位非 0（`flags` 高位、OPEN 的 reserved 字节、DATA 上置了 `report`）
- 声明长度超过单帧上限
- 一条流上出现第二个 OPEN（交换还没结束就复用流）
- `eof` 之后该流上又来帧
- 客户端越权发 `.peer` / `.multicast`
- datagram 帧出现在 QUIC 流上

这些都意味着对端的编码器坏了或在故意构造。同一个编码器产出的其他流同样不可信，
保留连接没有意义——这也是 HTTP/2 与 HTTP/3 的做法（分帧错误是 connection error，
不是 stream error）。

**业务级 —— 在该流上回一个错误帧，然后正常 fin**

- 路由不存在
- 在途配额满 / 单连接并发交换数超限
- 未认证 / 认证已过期
- 后端不可用或中途失败
- 网关还不认识的控制类型（控制类型是开放空间，用一个新取值不代表编码器坏了）

这些情况下字节流是合法的，只是这一次交换做不成。回错误帧让客户端拿到原因，
其他流不受影响。

**"首帧必须是 OPEN"是个例外：查不到交换的 DATA 帧只能丢弃，不能升级。**

网关分不清两种情形：客户端真的先发了 DATA，还是这次交换刚刚被业务级理由拒掉、
因此没有留下状态。后者在正常运行中就会发生——客户端收到错误帧时，后面的分片
早就在路上了。既然分不清就不能升级，否则一次配额拒绝会顺带杀掉整条连接。

丢弃是安全的：那一帧已经被完整解析，帧边界没有丢失，也没有任何字节被转发。
真正需要靠状态判定的两条（第二个 OPEN、`eof` 之后又来帧）都是无歧义的，
因为此时网关手上确实有这次交换的记录。

**不使用 RESET_STREAM。**

理由有两条。一是它只中止**发送方向**：网关在一条双向流上是客户端数据的接收方，
`picoquic_reset_stream` 只关掉网关→客户端那半边，客户端仍可继续发送，
于是违规反复触发、日志与 CPU 被白白消耗（要真正止住上行得再发 STOP_SENDING）。
二是 reset 会丢弃尚未送达的数据，所以"先回错误帧再 reset"这个组合里错误帧很可能
根本收不到——那还不如不 reset。

因此协议违规关连接、业务失败回错误帧，两者都不需要流级重置，也就不需要绑定
STOP_SENDING。

## 8. 成员归属与集群

`.peer` 与 `.multicast` 都需要"这个标识落在哪条连接上"。网关**不持有分布式应用状态**，
两者的解法不同，适用场景也不同。

**`.peer`（批量）：成员由后端逐次给出，网关不持有组状态。**
网关只维护本节点的 `dest_id → [connection]` 索引。后端发一帧带 N 个 `dest_id`，
落在本节点的直接投递。**不需要组成员表**——成员集合是后端的数据，每次随帧给出。

但"落在其他节点的怎么办"是未解决的：网关没有 `dest_id → node` 的映射，问题的来源见
§8.4、解法的分层见 §8.5。其中一种选路策略要求两级亲和，因此"`.peer` 不需要亲和"这句话
只在**单节点部署**下成立，不能当成 `.peer` 与 `.multicast` 的分界。真正的分界是
**成员表放哪**：`.peer` 的成员由后端每次给出，`.multicast` 的成员表在网关。

**`.multicast`：成员表在网关，不需要亲和。**
每个位置（节点 × Worker）各持有自己那份 `(realm, group_id) → [connection]` 索引，
投递指令发给所有位置，各自查本地索引。

本文档早先写的是"一个组播组的所有成员固定在同一个网关节点上（亲和）"。
**这句话是错的**，已更正。理由：组成员的落点由**各自的 `dest_id`** 决定，与 `group_id`
无关——一个协作会话的参与者是不同的账号，`hash(realm, dest_id)` 会把他们散布到各处。
所以 `hash(realm, group_id)` 对"成员在哪"毫无预测力，亲和在这里没有意义。

更正之后 `.multicast` 的价值反而**更清楚**了，而且不再依赖任何前置条件：

- 批量 `.peer` 的跨位置成本是 **O(目标数)** —— 每个 `dest_id` 各算一次 home、
  帧里还要塞下全部 id
- `.multicast` 的跨位置成本是 **O(位置数)** —— **与组成员数无关**

一个 5000 人的直播间：批量 `.peer` 要在帧里塞 40 KB 的 id 列表并算 5000 次 home；
`.multicast` 只是 8 字节组标识 × (节点数 × Worker 数) 次投递指令。

### 8.1 IM 群聊仍然应该用批量 `.peer`

亲和前提被移除之后，"IM 群聊不能用 `.multicast`"的理由变了，但结论没变。
现在的理由是**成员表放哪**：

- IM 群成员本来就是必须持久化的业务数据，后端每次随帧给出即可，网关无状态。
  让网关也存一份群关系，等于把业务状态搬进网关（破 §12.1 的不变量），
  而且要为"加群/退群/踢人"再建一条同步通路。
- 一个用户同时在几十个群里，`max_groups_per_connection` 这类内存预算会立刻绷不住。

所以场景分工是：

- **批量 `.peer`** —— IM 单聊、IM 群聊、以及任何"成员集合由业务侧掌握、且变动频繁"
  的推送。后端本来就知道成员是谁，网关不需要任何组状态。
- **`.multicast`** —— 游戏房间、文档协作会话、直播间，即**成员相对稳定、广播高频、
  成员数远大于组数**的场景。换来的是跨位置成本与成员数解耦。

两者都让后端的扇出成本保持 O(1)（发一帧而不是 N 帧），区别在成员表放哪。

### 8.2 扇出的真实成本

网关扇出是 **1 次读 + N 次写**。每次写 picoquic 都会把负载拷进该连接的发送队列——
每条 QUIC 连接有独立的加密上下文，密文无法共享，所以这份拷贝与加密开销不可避免。

1000 个目标 × 1 KB 负载 = 1 MB 的拷贝加加密。这是 QUIC 的固有成本，不是设计缺陷，
但容量规划时必须算进去：**"零拷贝"这个性质只对单目标投递成立，对扇出不成立。**

### 8.3 被否决的方案

网关持有组播成员关系并跨节点复制。这会让网关拥有分布式应用状态；而 SWIM gossip
是最终一致的、且是为节点成员设计的，不适合承载应用层的房间关系。

### 8.4 跨节点投递：问题从哪来

本文档早先写的是"其他节点的经已有的 forward 隧道转发"。**这句话是错的**，读过
`src/io/forward.zig` 之后必须更正：

- 隧道搬运的是**原始 UDP 数据报（QUIC 密文）**，接收侧解出 payload 后直接喂给
  picoquic（`Tunnel.runThread` → `LocalPacketRouter.forwardTunnel`）。它没有任何
  表达"请把这段应用数据投递给你节点上的 `dest_id` X"的能力。
- 帧头里的 `kind` 只有 `1 = request` / `2 = response` 两个取值，是**方向**而不是
  消息类型。u8 有余量，新增取值在线格式上可行，HMAC、防重放、`node_id → address`
  寻址都能复用，但接收侧需要一条与"喂 picoquic"完全不同的分支。

#### 根因：网关里有两套互不兼容的寻址方案

不是某处写错了，是两套为不同问题设计的方案第一次相遇。

**方案一：CID 内嵌位置（上行，早已建好）。** 客户端的 UDP 包可能落到任意节点，而
QUIC 连接状态只存在于一个节点的一个 Worker 上。解法是把归属编码进连接 id：
`CID = magic(2) | version(1) | node_id(2) | worker_id(1) | entropy(6)`。任何节点读 CID
就是 O(1) 判定，**不查表、不需要共享状态**。标识由网关在握手时自己选，位置就长在标识
里面 —— 自寻址，所以整个系统从来不需要一张目录表，也就从来没有建过。

**方案二：`dest_id`（下行推送，2a 才引入）。** 它的三个性质与上面逐条冲突：

- 由**认证服务**选，不是网关；
- 在**握手之后**才知道，而那时位置已被 CID 定死；
- 必须**与位置无关** —— 一个 `dest_id` 对 N 条连接（§5.6），一个内嵌位置描述不了
  N 个位置；而且它要跨重连保持稳定，否则后端无法寻址。

位置无关标识必然需要一张目录，而方案一的全部优雅之处正是"不需要目录"。

**为什么直到 2a 才暴露**：之前整个数据面是请求/响应驱动的，每个下行字节都是某个上行
请求的响应，回程映射在请求进来时就顺手记下了。请求从哪个 Worker 进来，响应就从哪个
Worker 出去，"在哪里"这个问题压根不会被问出来。`.peer` 推送是第一股不源自目标连接
自己那个 Worker 的流量。

一句话收束：**Thread-per-core 无锁 + CID 内嵌位置 ⇒ 不需要目录 ⇒ 没建目录 ⇒
引入位置无关标识 ⇒ 需要目录 ⇒ 两级都缺。**

#### 两跳都不知道

**第一跳：哪个节点？** 不存在任何 `dest_id → node` 的映射。已有的两样都不是它：

- CID 里的 `node_id` 只在"包已经在手上"时有用——入站报文的 CID 告诉你它归谁，
  方向与"我想主动找某个 `dest_id`"正好相反。
- SWIM membership 提供 `node_id → address`，回答"已知目标是 B 之后怎么发到 B"，
  不回答"B 是谁"。

因此 §8 里那句"按 id 分组"只有前半句成立：本节点的能靠本地索引判出来，剩下的
**不知道该发给谁**。

**第二跳：哪个 Worker？** 隧道帧头有 `target_worker_id`，由发送方填写；而
`dest_id → [connection]` 索引是 Worker 本地的（thread-per-core 无锁前提）。连接落在
哪个 Worker 与 `dest_id` 无关：

- `src/io/reuseport.c:51-56` 的 cBPF 校验 CID 的魔数 + 版本，不符就返回
  `LYUNE_REUSEPORT_FALLBACK`，落到内核默认 reuseport 哈希（按四元组）。
- 而客户端**第一个 Initial 包的 DCID 是客户端自己随机生成的**，不带我们的魔数，
  必然走 fallback。

所以**落在哪个 Worker 是客户端源 IP:port 的函数**，与 `dest_id` 毫无关系。

#### CID 是位置的标签，不能事后重贴

一个自然的想法是握手后用 `NEW_CONNECTION_ID` 换一个由 `hash(dest_id)` 派生的 CID。
这条不成立，原因比"协议不允许"更根本：

> **CID 标注状态在哪，不能决定状态去哪。**

- 节点级：网络把包送到任意节点，节点读 CID 判断归属再转发。CID 是用户态校验的**标签**。
- Worker 级更硬：reuseport BPF 直接读 CID 里的 `worker_id` 决定投给哪个 socket，
  是**内核级选择器**。

连接状态（picoquic 的加密上下文、拥塞状态、流状态）就在当初握手的那个 Worker 上。
事后换一个说"我在别处"的 CID，包会被投给一个没有这条连接状态的地方。而跨进程/跨节点
迁移 QUIC 连接状态是 QUIC 没有定义、picoquic 也不提供的能力。

**你不能给搬不走的东西重新贴标签。** 这条约束决定了下面所有方案的形状。

### 8.5 跨节点投递：分层与选路策略

关键结构性认识：**"投递通路"与"选路策略"是两层，前者必须建，后者可替换。**
早先把两者混为一谈，才会得出"必须先定一条路线才能开工"的结论——那个结论是错的。

#### 第一层：应用层投递通路（必须建，所有策略共用）

- **节点内（已实现）**：每个 Worker 一条应用消息队列（`io/handoff.zig` 的
  `MessageRouter`），槽位是一整帧（8 + 65535），深度进配置。
- **跨节点（已实现）**：走 `worker/peer_link.zig` 的 QUIC+mTLS 链路；见下面“跨节点为什么
  不能用 forward 隧道”。

**线格式必须带 `dest_id`，不能带发送方解析出来的 `(node, worker, connection)`。**
这是让第二层真正可插拔的唯一前提：

- 带 `dest_id` → 接收方查自己的本地索引，策略完全在发送侧，换策略不动线格式、
  不动接收侧。
- 带解析后的位置 → 策略被烤进线格式，换策略要同时改两端，滚动升级期间还得两种格式
  并存。

实现上更进一步：**转投的就是原帧本身**（`.peer` / `.multicast` / `.gateway` 的那一帧，
外加一个随消息传递的 `realm`）。接收侧走的是同一套 `dest_kind` 分派，只是**只做本地
投递、绝不再转投**——这就是防环的全部机制，不需要跳数或"已路由"标记。

`realm` **必须随消息传递，不能让目标 Worker 从帧里读**：realm 是网关按 SNI 定的
（§12.3），帧是后端给的。从帧里读就等于把隔离边界交给了消息内容。

槽位为什么不复用包队列的 2048 字节：那个数字是给 UDP 数据报定的（QUIC 包典型不超过
1500）。把应用消息绑上去会让协议层的 64 KB body 上限**只在跨 Worker 时**静默降级成
2 KB——同一个 API 在单 Worker 与多 Worker 下行为不同，是最难排查的失败模式。
分开之后各自按用途定尺寸：包队列是深队列浅槽位（吸收突发重传），应用消息队列是浅队列
深槽位（低频、一轮事件循环就排空）。深度进配置，**槽位不进配置**——它由协议决定，
调小就是静默截断。

#### 跨节点为什么不能用 forward 隧道，以及正确的载体

forward 隧道是**裸 UDP**。单个 UDP 数据报的载荷上限是 65507 字节，而隧道自己要占
32 字节固定头 + 最多 16 字节地址 + 32 字节 HMAC = 80，剩 65427。应用帧的上限是
8 + 65535 = **65543**。

**一整帧塞不进一个数据报，这是算术，不是设计选择。** 缺口只有 116 字节，所以只有
贴着上限的帧受影响——但"同一个 API 在单节点和多节点下行为不同"这条正是上面刚否决过的
失败模式，不能在跨节点这一跳重新引入。而给隧道加分片/重组等于在 UDP 上重新实现一遍
QUIC 已经做好的事（分片 id、乱序、超时回收、丢一片全帧作废）。

**因此跨节点的应用层投递走 QUIC，不走 forward 隧道。** 载体形态：

> **一个网关节点，对它的对等节点来说，就是"一个会推送的后端"。**

节点 A 作为 QUIC 客户端连到节点 B，在上面说**同一套帧协议**：`.peer` / `.multicast`
的 OPEN + 目标列表。B 侧收到的是一条 peer-initiated 流，走的正是它已经写好的
`.peer` / `.multicast` 扇出路径——不需要新的线格式，不需要新的分派分支。

三个附带收益：可靠有序（不会因为丢一个分片作废整帧）、拥塞控制、以及加密都由 QUIC
提供；**帧长不再有额外上限**，64 KB 一路通到底。

两处细节，都已定并落地：

- **realm 怎么带**：`.peer` / `.multicast` 的 OPEN 里 `group + route_key` 那两字节本来
  就是保留的（§5.1），而 `RealmId` 恰好是 u16 —— 正好放进去。零新增线格式。
  它只在**对等节点连接**上被这样解释；客户端/后端连接上那两字节仍然保留、网关不读。
  实现见 `FrameHeader.realmHint()`。
- **对等节点怎么证明自己是对等节点：mTLS，独立端口。** 一条客户端连接绝不能获得
  `.peer` 权限，所以判据必须是**结构性的**而不是"一个要被正确设置的标记"。

#### 对等身份用 mTLS，而不是应用层握手

集群链路走**独立的监听端口**（`cluster.peer_port`），该端口要求由**私有集群 CA**
签发的客户端证书（`picoquic_set_client_authentication`）。于是：

> **在这个端口上握手成功 == 对端持有集群 CA 签发的证书 == 对端是一个网关节点。**

这条等价关系就是全部的身份校验。因此**不需要**任何应用层握手：没有 `cluster_hello`、
没有挑战 nonce、没有 HMAC、没有防重放窗口、没有时钟同步。权限判据变成"这条连接是从
哪个 socket 进来的"——一条客户端连接没有任何方式能获得它，因为它落在另一个 socket 上。

关键取舍：**证书不需要告诉我们"对端是节点 7"，只需要告诉我们"对端是网关节点"。**
这一点很重要，因为已核实 picoquic / picotls **不把已验证的对端证书内容交给应用层**
（`ptls_verify_certificate_t` 只回 0/-1），要拿 CN/SAN 得自己写 picotls 回调。
而我们不需要：`node_id` 不授予任何东西（realm 写在帧头，投递只查本地索引），
所以它可以由未签名的应用层字段给出，只用于日志。

对等节点能指定任意 realm，这不是新增的信任——它本来就持有所有 realm 的连接。

比共享 PSK 强一档的地方：一把 PSK 泄露等于整个集群失守且无法定点撤销；证书可以按
节点吊销、短有效期轮换。

代价两条，都要写清：

- **面向客户端的端口绝不能开 `require_client_auth`**，否则普通客户端也要带证书。
  两个监听器因此必须是两个 socket、两个 picoquic 上下文（那是上下文级开关），
  配置也分成 `server.*` 与 `cluster.peer_*` 两份。
- **证书成了多节点的硬前置**：集群 CA + 每节点 cert/key 必须先有。这与 §10.1 的
  mTLS 是同一份运维负担，不是新增的。三项证书留空即不启用集群链路，此时跨节点目标
  会被回报为不可达而不是静默丢弃。

签发节点证书时有一条容易漏的要求：出站链路连集群端口时用的 SNI 是 **`lyune-cluster`**
（`worker/peer_link.zig` 的 `peer_server_name`）。对面不从它解析 realm——集群监听器
没有 realm 概念，realm 走帧头——但 TLS 要求客户端给一个 server_name，而证书校验会
核对它。**因此集群 CA 签发的节点证书必须把这个名字放进 SAN。** 漏了它的症状是
"跨节点投递全部回报不可达"，从这个现象看不出根因在证书。

#### 第二层策略 A：广播

投递指令发给集群里每个节点，节点内再交给每个 Worker，各自查本地索引，命中就投；
**查不到是正常情形**，不是错误。

- 完全无状态，不动任何现有不变量，两跳一起解决，客户端零改动。
- 成本在**查询侧**：每次跨节点推送 O(节点数) 次网络发送 + O(节点数 × Worker 数) 次查表。
- 代价不只是带宽：**投递回报退化**。发起方无从知道有没有别的位置命中，`unreachable`
  只能表达"本位置没有"，后端会为在线用户白转一次离线存储（§5.5）。

它不是"将来要扔掉的临时方案"——它就是第一层加上最简策略。`.multicast` **永远**用它
（组成员的落点由各自的 `dest_id` 决定，与 `group_id` 无关，见 §8）。

#### 第二层策略 B：`hash(realm, dest_id)` 亲和（`.peer` 的默认策略）

先说清最反直觉的一点：**hash 不是查询，是约定。**

`hash(dest_id)` 对连接实际在哪一无所知，它只是挑了一个**任意但所有节点算得一致**的
位置。要让这个答案变成真的，只有一条路：**把连接搬到函数算出来的地方去**。
所以我们不是在算"连接在哪"，而是在算"连接必须去哪"——重定向因此是必需的，
不是补丁。

不变量是：**每一条带 `dest_id` 的活连接，都位于 `hash(realm, dest_id)` 算出的位置上。**
第一次连接必然违反它（落点由网络决定，此时还不知道 `dest_id`），所以必须强制：

```
客户端连上来（落在网络选的任意节点 A）
  → 握手完成 → 认证 → 网关学到 dest_id = X
  → 算 home = HRW(realm, X)
  → home 节点 == A ？ 是 → 正常服务
                      否 → 先把认证响应回给客户端（凭据是有效的，只是地方不对）
                           再回 .gateway 的 redirect 帧「去节点 B，地址 …」
                           带 AppError.redirected 关闭连接
```

**不在 home 上就不绑定 `dest_id`、不置 `authenticated`。** 这样即使关闭在竞态里慢了
一步，这条连接也已经既不可被寻址、也发不了数据帧。反过来"就在本地先服务着"会让
后续按 hash 定向的推送漏掉它，而漏掉的表现是消息静默丢失。

拿不到 home 地址（membership 里没有它、或本节点用的是临时端口）时**不重定向**，
退化成就地服务并记一条 warn：宁可牺牲一次亲和，也不能把一个错地址交给客户端。

之后任意节点收到"投给 X"时纯计算命中，零查表。

多 realm 下亲和键必须是 `hash(realm, dest_id)` 而不是 `hash(dest_id)`——否则大 realm 的
热点会直接传染给小 realm，理由与后果见 §12.6。

#### 用 HRW 而不是哈希环

选址用 **rendezvous hashing（HRW）**：给每个候选节点算一个 `mix(key, node_id)` 分数，
取最大的那个。

它与哈希环同样满足"节点数变化时只有 1/N 的键漂移"这条关键性质，但**不需要构建环、
不需要虚拟节点、不需要任何运行期状态**——它是候选列表的纯函数。而 `% node_count` 不行：
加一个节点会让几乎所有键的 home 同时漂移。

代价是 O(节点数) 次乘法，只在跨位置投递时才算，可忽略。

#### 节点列表是快照，这是这条路线唯一的脆弱点

两次计算必须**同意**，这要求两样东西一致：同一个 hash 函数（代码里写死，没问题），
以及**同一份节点列表**（来自 SWIM，最终一致）。视图不一致的窗口里两次计算得到不同
答案，表现是消息静默丢失。

实现上还有一层：`membership.Table` 的零锁读接口是按 node_id 逐个 lookup 的（遍历只允许
SWIM 线程做），而 HRW 需要完整候选集合。每个目标都扫一遍全表会让扇出退化成
O(目标数 × max_nodes)，所以 Worker 在自己的周期定时器里抄一份快照。**快照必然滞后**，
这不是实现引入的问题，而是上面那条脆弱点的具体形态。

**三道防线，各解决不同的一半，缺一不可**（全部已实现）：

1. **HRW 限制漂移范围** —— 加第 N 个节点只搬约 1/N 的键（`% node_count` 会搬走几乎全部）。
2. **成员变更后 30 秒内双查** —— `placement.previousHomeNode` 记住变更前那份视图，
   `egress.markHome` 往新旧两个 home 各发一份，`acceptedHome` 结算时也看两个。
   它解决的是**视图不一致**：窗口内新旧两份的并集必定包含真正的位置。窗口只需覆盖
   SWIM 收敛（gossip 是 O(log N) 轮，秒级），取 30 秒是留余量——窗口偏长只是漂移的那
   一小部分键多发一份，窗口偏短是消息静默丢失，两边不对称。
   **不会造成重复投递**：一条连接只存在于一个位置上，另一个位置查不到索引就什么也不做，
   与广播策略下"查不到是正常情形"是同一件事。
3. **窗口关闭后把漂移的连接赶回新 home** —— `worker.rehomeDrifted` 扫本 Worker 的连接，
   `isHomeNode` 为假的就走 `auth.redirectToHome`（复用认证时那条 `redirect` +
   `AppError.redirected` 通路）。它解决的是**不变量被破坏**：连接是长寿的（IM 客户端挂
   几小时很正常），而它的 home 会因为**别人**扩容而漂走。只有第 2 道的话窗口一过这条
   连接就**永久**收不到推送，而且没有任何报错提示。每轮限额 `rehome_per_tick = 16`——
   注意它限的是**检查条数**而不是重定向条数（`peer_node`、未绑定 `dest_id`、已在 home
   这三种跳过同样消耗额度），所以它保证的是"每轮最多推进 16 个槽位"，扫完一张一万连接
   的表需要 625 轮。实际重定向速率总是 ≤16/轮，扩容因此是涓流而不是重连风暴。

窗口内 `isHome` / `isHomeNode` 都放宽到"新旧任一命中"。第二条尤其重要：此刻本节点的
视图可能比别人新也可能比别人旧，按一份不稳定的视图去重定向会让客户端在两个节点之间
来回弹；窗口内两个位置都算合法，窗口一过再由第 3 道统一赶回去。

#### 这条路线的完整形态

1. **HRW 选址** —— 已实现（`foundation/placement.zig`）。
2. **`redirect` 控制帧 + `AppError.redirected`** —— 已实现（线格式见 §7.4）。
   这是对外契约的变更，客户端 SDK 必须实现。
3. **客户端缓存 home 地址**：`redirect` 的 body 带 "host:port"，SDK 存下来，下次重连
   直接拨它。这就解决了节点级，**不需要任何服务端签发的凭据**——记忆放在客户端。
   home 因扩缩容漂移时缓存过期，客户端连到错节点、再吃一次重定向、更新缓存，**自愈**。
4. **placement hint 进 initial DCID**：解决 Worker 级。见下面"为什么不用 NEW_TOKEN"。
5. **扩缩容期间的双查 + 漂移重归位** —— 已实现（见上面三道防线）。

#### 为什么不用 NEW_TOKEN（已核实：picoquic 不支持）

原本的设想是把 `dest_id` 签进 QUIC 的 `NEW_TOKEN`，让任意节点在握手前解出它。**这条路
不通**：picoquic 的 token 完全由内部生成、加密、校验，且绑定 IP，应用层既拿不到内容也
插不进校验逻辑（`libs/picoquic/picoquic/tls_api.c:2797-2911` 是内部函数，不在公开 API 里）。

替代路径不依赖 picoquic 暴露任何东西：**QUIC 规定客户端首个 Initial 包的 DCID 由客户端
自选**（8–20 字节，服务端必须接受）。而我们的 reuseport cBPF（`src/io/reuseport.c:51-58`）
本来就是从 DCID 里读魔数 + 版本 + `worker_id`。所以让 SDK 把初始 DCID 构造成那 12 字节
格式、`worker_id` 填对，**内核态就把首包投给了正确的 Worker**——不需要节点内交接，
也不需要 picoquic 配合。握手之后服务端下发自己的 SCID，客户端切过去，所以这个 DCID
只在第一个 flight 里起作用，而那正是唯一需要它的时刻。

三条必须写死的约束：

- **客户端不该知道哈希函数与 `worker_count`。** 网关给它一段**不透明的 placement hint**，
  客户端下次连接原样填进 DCID。这样扩缩容改了 `worker_count`，客户端零改动。
- **hint 绝不能包含完整 CID。** 网关生成的 CID 尾部是 entropy；把完整 CID 交给客户端复用，
  就给了它主动撞上一条在用连接 CID 的机会（撞上也拿不到密钥、包会被丢弃，但没必要给这个
  机会）。**hint 只含定位段，entropy 由客户端随机填。**
- **hint 不需要 MAC。** 它只回答"去哪"，不回答"你是谁能干什么"：伪造它最坏是客户端把
  自己钉到某个 Worker 上制造热点，而身份始终只来自 `auth_success`。这是可用性问题，
  比机密性低一档——比原来的 token 方案还省一层。

**未验证**：picoquic 服务端对客户端自选 12 字节 DCID 的实际行为。协议上必须接受，
但要实测（见 §13）。这条比原来的 token 接口好验证得多，写个小客户端测试就能确认。

另一个必须记下的代价：**均衡粒度从"连接"退化成"账号"**。§5.6 定了一个 `dest_id` 对
N 条连接，亲和会把一个账号的所有设备钉在同一个 Worker 上。对扇出是好事（纯本地），
但设备数不均或有大号时会出热点。

#### 被排除：进程级 `dest_id → (worker, connection)` 索引

一次查表命中第二跳，但要跨线程读写，破坏"Worker 状态线程私有、无锁"这条前提。
而且**它不解决第一跳**——节点级仍要另配机制，那要么是被 §8.3 否决的分布式状态，
要么是一张外部路由表（Redis 之类），后者会让网关的横向扩展依赖一个集中式组件。
所以它只是半条路线，不单独成立。

#### 判据与当前默认

- **推送频率高 × 集群大** → 亲和划算（查询免费）
- **重连频率高 × 集群小** → 广播划算（建连免费）

**默认是亲和**，理由不是成本结构（当前只有 1 个节点，两者的差别还看不出来），而是两条
与规模无关的：

1. **契约现在改最便宜。** 客户端 SDK 还不存在，给一个不存在的 SDK 加"必须处理
   `redirect` + 必须缓存 home 地址 + 必须复制 placement hint"是免费的；等 SDK 铺出去了
   再加就是对所有已部署客户端的破坏性变更。SaaS 定位让这条更强——SDK 是对第三方的
   产品接口（§12.6）。
2. **广播会让投递回报退化**，后端要为在线用户白转一次离线存储（§5.5）。

**两种策略共用一条通路、一个"目标集合"函数**，不是两条代码路径：亲和模式下集合是
`{home}`，广播模式下集合是全部位置。这一点是有意守住的——两者的正确性不变量不同
（亲和要强制重定向、广播不要），做成两套实现的话运维配错就是静默的消息丢失，
而这类错误没有任何报错会提示。

`.multicast` **不受这个开关影响**，永远走广播（理由见 §8）。

一个必须提前说清的坑：**策略配成广播时网关永不发 `redirect`，那条路径就永远没被跑过**，
真开启时大概率是坏的。因此一致性测试必须覆盖它，别让它成为死代码。

## 9. 与 BackendTransport 的关系

协议只表达"目的地是哪个服务"，不表达"用哪条传输路径"。路径由服务端注册关系决定：

- `TransportPath.direct` —— 网关直连后端，性能优先
- `TransportPath.relay` —— 经中继扇出（尚未实现）

需要注意的区分：`relay` 解决的是**上行侧**扇出（一条上行发布到多个后端/topic），
它**不解决** `.multicast` 的下行扇出。后者必须在网关实现，与 transport 选型无关。

## 10. 认证与准入

网关做**连接准入**，不做**请求授权**。准入是资源管理（这条连接是否被允许继续占用
槽位、CID、后端流配额），授权依赖业务语义，必须留在后端。

网关不解析 token：`auth_request` 原样转给配置指定的认证服务，只根据响应帧类型
（`auth_success` / `auth_failure`）给连接打标记。token 的形态、吊销机制对网关不可见。

这条边界不只是洁癖：它是"让接入方自己鉴权"的 SaaS 定位能成立的前提（§12.1）。

### 10.1 网关 ↔ 后端必须双向认证

当前是单向的：网关验证后端证书，后端不验证网关（后端连接配置里没有客户端证书）。
这意味着任何能连上后端端口的东西都能冒充网关。

不变量应当是：**`isReady()` 蕴含双向认证已完成**。这不需要额外状态机——
配上 mTLS 之后，对端身份校验失败意味着 QUIC 握手不会完成，连接永远到不了 ready，
"认证失败"与"没有可用 transport"是同一件事。

§1.2 里"下行不校验"的正当性依赖这一条先成立。

**多 realm 下这条从"应该补"升级为"上线阻塞项"**：多个接入方的后端都在网络上，
单向认证意味着任何能连上 realm B 后端端口的东西都能冒充网关——包括 realm A（§12.5）。

### 10.2 准入状态需要生命周期

当前 `authenticated` 一旦置位永不失效，意味着 token 过期、账号吊销都无法反映到
已建立的连接上。需要的是：

- 认证服务在 `auth_success` 里带回 TTL（网关解析的是自己协议的字段，不是 token）
- 连接记 `auth_expires_at`，过期后数据帧被拒，客户端需重新认证
- `kick_off` 作为加速手段：立即中断，但**吊销的权威在认证服务**——
  没有 TTL 兜底的 kick 是无效的，客户端立刻重连就又进来了

因此顺序是：TTL 是地基（给出"最迟 T 秒后失效"的正确性保证），kick_off 是地基上的
延迟优化。只做一件事的话做 TTL。

### 10.3 auth_success 的 body 布局

网关需要从认证结果里取两样自己的东西：这条连接可被寻址的 `dest_id`（§5.6）与准入
有效期（§10.2）。因此 `auth_success` 的 body 有一段**网关自有的定长前缀**：

```
偏移  长度  字段
0     8     dest_id (u64, 大端)；0 表示"不可被寻址"
8     4     ttl_seconds (u32, 大端)；0 表示"不过期"
12    ..    opaque，网关不解析，原样透传给客户端
```

三点说明：

- **这不违反"网关不解析 token"。** 网关解析的是自己协议的字段；token 的形态、
  签名方式、吊销机制依然完全不可见。前缀之后的字节网关一个都不看。
- **整段 body 原样回给客户端**，不剥离前缀（同 §5.3 的理由：剥离要重新编码帧头）。
  客户端因此也能读到自己的 `dest_id` 与有效期，这是它需要知道的。
- **body 短于 12 字节的 `auth_success` 判为 invalid**，按认证失败处理。宁可拒绝也不
  能把一个截断的响应当成"认证通过且不可寻址且永不过期"。

多 realm 下 `dest_id` 的作用域是**该 realm**，不是全局；网关落索引时必须带上由 SNI 确定的
realm 身份（§12.2、§12.3）。接入方在自己的命名空间里怎么分配 `dest_id` 是它的自由。

`auth_failure` 的 body 仍然是纯文本原因，没有前缀——失败路径不需要这两个字段。

## 11. 分阶段实施

**第一步（已实现）：流上的部分**

- `frame_type`（OPEN / DATA）、`flags`、`body_len` u16、64 KB 上限
- `dest_kind` 四个取值全部定义，但只实现 `.gateway` 与 `.service`；
  客户端发出 `.peer` / `.multicast` 按越权关连接
- 删除 `magic` / `version` / `seq` / `need_ack` / `sof` / `TransportMode`
- 上行两条转发路径合并为一条

落地位置：`src/protocol/frame.zig`（帧头与白名单解码）、`codec.zig`（编码器与
就地扫描器）、`framing.zig`（跨回调残帧补齐）、`src/worker/ingress.zig`（分派与
错误分级）、`src/worker/connection.zig`（按流的交换状态）。

`.gateway` 的流式交换（§5.1）线格式已允许但尚未打通，见该节末尾。

**第二步：推送与组播**

读过 `src/io/forward.zig` 与 `src/backend/direct.zig` 之后，这一步切成三段：

- **2a 单节点单 Worker 内的 `.peer` 推送（已实现）**：`auth_success` 前缀解析（§10.3）、
  `dest_id → [connection]` 定容索引、准入 TTL、后端主动发起流的接纳、`.peer` body
  前缀解析与本地扇出、`flags.report` 投递回报、网关主动开流推送。
- **2b 跨位置投递**：分两层，见 §8.5。
  - **跨 Worker（已实现）**：`io/handoff.zig` 的 `MessageRouter`（每 Worker 一条应用
    消息队列，槽位一整帧）、Worker 的第二个 `xev.Async`、`egress.deliverHandoff`
    （只做本地投递、绝不再转投）。
  - **跨节点（已实现）**：载体是**节点间 QUIC 链路**而不是 forward 隧道，理由是算术性的
    （一整帧塞不进一个 UDP 数据报）。
    - 接收侧：集群监听器（`cluster.peer_port` + mTLS，`quic/config.zig` 的
      `require_client_auth`、`worker.zig` 的第二个 `ServerDriver` 与
      `handlePeerConnection`）、`ConnectionContext.peer_node`、ingress 的对等节点白名单
      （`openPeerNodeExchange`：只准 `.peer`/`.multicast`，realm 取自 `realmHint()`）、
      egress 的 `deliverFromPeer`（本地投递 + 一次节点内转投，总跳数限死 2）。
    - 发送侧：`worker/peer_link.zig` 的 `PeerLinks`——自己持有一个 QUIC 客户端 + 一张
      定容链路表，`patchRealm` 把 realm 打进 OPEN 头保留的两字节（拷到 scratch 再改，
      不就地改原帧），指数退避由 Worker 的轮询定时器推进，接进 `RouteSet.flush`。
    - 链路不可用时 `send` 返回 false，目标随后被回报为不可达，**不静默丢弃**也**不排队**
      ——排队意味着后端以为消息在路上，而它可能永远发不出去。
  - **选路策略（已实现）**：`foundation/placement.zig` 的 HRW，`broadcast` / `affinity`
    两种共用一条通路，配置项 `cluster.placement`，默认 `affinity`。
- **2c `.multicast`（已实现）**：`(realm, group_id) → [connection]` 的定容边池（多对多，

## 12. 隔离域模型（realm / IM SaaS）

网关除自用之外还要作为 **IM SaaS** 对外提供：第三方接入方使用本网关 + 官方 SDK，
而**鉴权由接入方自己的服务端完成**。这个定位不改协议线格式，但改了若干命名空间与
配额的语义，所以单独成节；被影响的章节各留一句指回这里。

### 12.0 为什么叫 realm 而不是 tenant

需要的概念是"**标识只在其内部唯一的管理边界**"：`dest_id`、路由键、组播组标识都只在
一个边界内有意义。`realm` 正是这个语义的既有术语（Kerberos realm、HTTP/SASL 认证的
realm），且三点契合：

- **对所有权中立**，不含计费与商务含义。自用部署就是"一个 realm"，而 `tenant` 天然
  暗示"有客户"，是业务视角而非网关视角。
- **建立位置吻合**：它由认证边界确定，而这里的 realm 恰好就是"哪个认证服务 + 哪套路由"。
- **读起来是限定词**：`realm + dest_id` 是全限定目的地，与 Kerberos 的 `principal@REALM`
  同构。

排掉的候选：`namespace`（与本文档里"命名空间"这个普通名词打架）、`domain`（超载严重，
且它字面就是 SNI 主机名，容易让人以为键是那个字符串）、`zone`（像可用区 / DNS zone）、
`app_id`（回到业务视角，且客户端自称的 id 不可采信，见 §12.3）、`scope` / `partition`
（太泛 / 像数据分片）。

实现见 `src/foundation/realm.zig`。

### 12.1 三条已经成立的地基

下面三条当初是为"职责边界"做的决定，不是为 SaaS，但恰好是多 realm 能干净的前提：

- **网关不解析 token**（§10）：每个 realm 的认证服务校验自己的 token，网关只看
  `auth_success` / `auth_failure`。网关永远不需要知道任何 realm 的认证方案。
- **`dest_id` 由认证服务下发**（§10.3）：身份标识由 realm 自己分配，网关只当它是不透明的
  8 字节键。
- **`.peer` 成员由后端每次随帧给出**（§8）：网关不持有任何 realm 的群关系数据。

合起来是一条不变量：**网关里不存 realm 的业务状态。** 这条要一直守住——一旦网关开始存
realm 数据，隔离就从"命名空间加个前缀"变成"数据面里的权限系统"。

### 12.2 命名空间隔离（已实现）

realm 会**独立**分配标识，而网关的键原先是全局的，最坏后果是**跨 realm 消息泄露**。
现在所有命名空间键都带上了 realm：

- **`(realm, dest_id)`**：`ConnectionManager.dest_index` 的键（`worker/connection.zig`）。
  realm A 的用户 123 与 realm B 的用户 123 是两条独立的链，扇出只遍历推送来源 realm 的那条。
- **`ScopedRoute = (realm, group, route_key)`**：注册表的键（`backend/registry.zig`）。
  A 的 `(1,0)` 与 B 的 `(1,0)` 指向不同 transport 实例。启动期校验拒绝重复键——
  它原先会静默顶掉前一个注册。
- **认证服务路由**：`auth_policy.route` 仍是单个 `(group, route_key)`，但查表时补上连接的
  realm。于是每个 realm 在同一个路由键上注册自己的认证服务，不需要 per-realm 策略配置；
  某个 realm 没注册就认证不过（失败关闭）。
- **`(realm, group_id)`**：组播成员索引的键（`ConnectionManager.groups`）。它与
  `dest_index` 共用同一份 `HeadTable` 实现，因此隔离规则也完全一致。三处一起才够：
  索引键带 realm、`joinGroup` 不接受 realm 参数（从连接上下文取）、以及后端 →
  网关的成员变更**校验发起方 realm 与目标连接 realm 相等**。少了第三条，realm A 的
  后端拿一个猜中的 `conn_token` 就能把 realm B 的连接塞进自己的组，从而收走那个组的
  全部广播——比消息泄露更糟，因为它是持续的。
- **跨位置转投的 realm**：`AppMessage.realm` 随消息传递，目标 Worker **不从帧里读**
  （`io/handoff.zig`）。帧是后端给的，realm 是网关按 SNI 定的；从帧里读就等于把隔离
  边界交给了消息内容。

realm 写进 `ConnectionContext` 后不可变，`bindDest` / `joinGroup` 都不接受 realm 参数
——它们从连接上下文自己取，免得给调用方一个"把标识绑进别的 realm"的机会。

#### 顺带修掉的一个更早的串话

做上面这件事时发现：后端流句柄（`sendStream` 的返回值）**只在单个 transport 实例内部唯一**
——direct 实现用 `conn_id << 48 | stream_id` 合成，而 `conn_id` 是每个实例各自从 0 开始编号
的。而在途表与推送重组缓冲是全 Worker 共享的、只按句柄建键。因此**只要配置了两条路由**，
两个实例就会发出同一个句柄，后一次登记顶掉前一次，A 的响应被写进 B 的客户端流。

这不是多 realm 才有的问题，单 realm 多路由就会触发；多 realm 下它会绕过上面所有的键修正。
修法是把实例身份并进键里：`StreamKey = (transport 实例, 句柄)`（`worker/inflight.zig`，
身份取 `BackendTransport.id()` 即实现指针）。`BackendStream` 直接存整个 `StreamKey`，
这样"transport 中途消失"那条分支也还能删掉在途条目。

### 12.3 realm 只能来自 SNI

**必须在 TLS 层确定，不能取自帧内容。** 三条理由：

1. **由证书链背书**，不是客户端自称。
2. **在任何应用数据之前就可知**——握手阶段就有，而选路与配额判断需要它。
3. 若让客户端在帧里带 `app_id`：伪造它拿不到别人的消息（绑定仍然只来自那个 realm 的认证
   服务），但足以驱使网关去连接任意 realm 的认证服务——一条免费的放大 DoS 通路。

形态：每个 realm 一个域名（`realm-a.gw.example.com`），网关在握手时读 SNI 定 realm，
写进 `ConnectionContext`，此后所有寻址与配额都带上它。

**已核实的两条 picoquic 事实：**

- `picoquic_tls_get_sni(cnx)`（`libs/picoquic/picoquic/picoquic.h:469`）可用，`@cImport`
  已自动暴露，不需要加绑定。**可用时机是握手完成后**（`.ready` 回调里），也就是连接注册
  进管理器的那一刻——realm 因此只能在连接就绪时确定，不能更早。
- **不存在按 SNI 选证书的钩子**：证书挂在 `picoquic_quic_t` 上，picoquic 没有 SNI
  callback。因此多个 realm 域名要么共用一张带多个 SAN 的证书，要么每个 realm 起一个独立
  QUIC 实例。这是运维约束，不影响协议。

**SNI → RealmId 的映射不能用哈希。** 哈希会在一条安全边界上引入碰撞可能，而碰撞就是静默
的跨 realm 泄露。用配置显式分配的 id，碰撞概率为零，代价只是多一段配置。未登记的 SNI
在多 realm 部署下**失败关闭**（拒连），否则一个拼错的域名会静默落进别人的命名空间。

**配置形态**（`foundation/config.zig`，解析表在 `foundation/realm.zig`）：

```json
"realms": [ { "server_name": "a.gw.example.com", "id": 1 } ],
"backend": { "direct": { "routes": [ { "realm": 1, "group": 1, "route_key": 0, ... } ] } }
```

`realms` 留空 = 单域部署，任何 SNI 都落进 `realm 0`，路由的 `realm` 也必须是 0。一旦登记了
任何域名就切成失败关闭。SNI 比较**不区分大小写**（RFC 6066 要求），重复登记同一域名在启动期
被拒——否则第二条会静默失效。SNI 原文不写进日志：它是对端可控的字节串。

### 12.4 配额必须按 realm

这些上限本来全是**每 Worker 全局值**，一个吵闹的 realm 能把它们吃干、饿死其他所有人：

- `max_connections`（会话槽位池）
- `inflight.max_requests`（回程映射与认证等待表）
- `ingress.max_exchanges_per_connection`
- `egress.max_push_streams`
- `connection.max_groups_per_connection` 对应的**组播成员边池**
  （`max_connections × max_groups_per_connection`）
- `cluster.message_queue_capacity`（每 Worker 的应用消息交接队列）
- `backend.pool.recv_slots`（每 Worker 共享的后端接收槽位池）

这件事与"启动期一次分配"的定容模型有张力：在一个共享的固定池上做按 realm 配额，要么
**预留**（每个 realm 切一块，小 realm 浪费、大 realm 封顶太早），要么**加权准入**
（共享池 + 按 realm 计数与阈值，复杂但不浪费）。

**已定：加权准入**，实现在 `foundation/quota.zig`。决定性理由是预留与"realm 注册要动态"
（§12.5）直接冲突——池是启动期定容的，新增一个 realm 就得重切份额，也就是要重启。
另两条：预留在机器空闲时也封顶大 realm（资源明明有却拒绝），小 realm 的预留份额是
永久浪费的 RSS。

形态：**水位线（默认 70%）以下无条件放行**，以上才按公平份额（容量 / 活跃 realm 数）
只拒超额的那个 realm。等于"只在争用时才讲公平"。份额的分母只在某个 realm 占用发生
0↔1 跃变时重算——每次 acquire 都数一遍是 O(max_realms)，在热路径上太贵。

**五个池全部已接**，各自的记账点与拒绝语义：

- **会话槽位池**：`ConnectionManager.add` / `remove`。超额返回 `RealmQuotaExceeded` 而不是
  `TooManyConnections`——池里还有空位时，运维必须能区分"整机满了"（要扩容）和"你这家
  超额了"（调权重或让它收敛）。
- **组播成员边池**：`joinGroup` / `releaseGroupEdge`，同样返回 `RealmQuotaExceeded`。
- **在途请求表**（`inflight.max_requests`，回程映射与认证等待表各一份配额）：
  `reserveRoute` / `reserveAuth` 返回 `Admit{ok, table_full, realm_over_share}`。realm 随条目
  存在 `Route` / `PendingAuth` 里，因为**三条回收路径里有两条**（连接关闭、过期兜底）跑的
  时候连接可能已经从管理器摘掉了，反查拿不到 realm。两张表各自只有**一个删除出口**
  （`dropRoute` / `dropAuth`），配额递减贴在那里，三条回收路径都经由它。
- **后端共享接收槽位池**：`SlotArena.take` / `release`。realm 钉在 `SlotList` 上（一条后端
  连接归一个 `DirectTransport`，而 transport 的键含 realm，所以一条队列绝不混 realm），
  并在取格时抄进 `Slot`——归还只有一个入口且手里只有下标，realm 必须能从槽位自己读出来。
  超额时整段拒绝（与容量不足同一条路径），因为截断一条可靠流是静默数据损坏。
- **应用消息交接队列**：`RingQueue.push` / `pop`，超额返回 `RealmOverShare`（与 `QueueFull`
  分开：前者查接入方，后者查目标 Worker 的消费侧）。这条队列记的是**当前积压**而不是
  累计量，两处记账都在队列的锁内完成——`push` 在生产者线程、`pop` 在消费者线程，
  放到锁外就是数据竞争。包队列（`ForwardPacket`）**没有**这个维度：它搬的是未解密的 UDP
  数据报，而 realm 由 TLS SNI 决定，那时还读不到，所以按 T 有无 `realm` 字段做 comptime 分支。

不需要接的两项：`max_exchanges_per_connection` 与 `max_push_streams` 本来就是**每连接**
的上限，而连接数已经被配额约束，所以一个 realm 的影响面已经被间接限住了。

三个池各有一个 realm 特有的放大效应，这也是它们必须单独接的理由：

- **组播成员边池**：A 的用户每人进 8 个组就能把边池占满，之后 B 的 `join_group` 一律
  返回 `TooManyGroupMemberships`。它是**明确拒绝**而不是静默无操作（否则表现成
  "B 的某些人收不到组广播"），但拒绝本身就是一次跨 realm 的可用性影响。
- **应用消息交接队列**：`.multicast` 的跨位置投递是广播，所以 A 的一条组播会在**每个**
  Worker 的队列上占一格——包括只承载 B 的连接的那些 Worker。队列满时丢弃是可观测的
  （`MessageRouter.dropped`），但同样是跨 realm 影响。
- **后端接收槽位池**：它是从"每条后端连接 2 MiB"收敛来的（`backend/pool.zig`），
  收敛的代价就是从此可以被跨 realm 争用。`pool.Config.max_slots_per_conn` 只挡住了
  最糟的形态（一个卡住不取的后端把整池吃干），但那是**按连接**的上限，不是按 realm——
  一个 realm 配 20 个副本就能占到 20 份，realm 份额才是真正的那道闸。

这几条不是设计缺陷，是"共享定容池 + 多 realm"这个组合的必然结果。**`max_slots_per_conn`
是这套方案的第一块砖**：它证明了"共享池 + 按持有者计数 + 超限明确拒绝"这条路走得通，
realm 级配额只是把"持有者"从连接换成 realm。

一条贯穿五个池的实现纪律：**计数的增减必须贴在池的取/还函数里，绝不放在调用点。**
漏掉一条归还路径的后果是那个 realm 的配额被永久蚕食，症状是"这家接入方的用户过几天
就连不上了"，极难定位。因此每个池都有一条"一轮建立-销毁之后计数归零"的用例。

### 12.5 被 SaaS 抬高优先级的两项

- **§10.1 的 mTLS 从"应该补"变成"上线阻塞项"。** 多个 realm 的后端都在网络上，网关→后端
  单向认证意味着任何能连上 realm B 后端端口的东西都能冒充网关——包括 realm A。
- **realm 注册必须是运维面的动态能力。** §5.1 已经明确"改路由表属于运维面"，方向一致。
  **已实现**：SIGHUP 重读配置文件，只接受新增，形态与理由见 §12.7。

### 12.6 对选路策略的影响

- 亲和键变成 `hash(realm, dest_id)`。好处是一个 realm 的用户会散布到所有节点；但
  **按 realm 的热点依然存在**（大 realm vs 小 realm），而且 realm 级配额与节点亲和会
  互相纠缠。
- **"契约先行"的论据变强**（§8.5 策略 B）：SDK 不再是内部组件，而是对第三方的产品接口。
  趁现在没有任何外部使用者，把重定向与 placement hint 一次性定对，比以后对着一堆已部署
  客户端做破坏性变更便宜得多。

### 12.7 动态注册接入方（配置热加载）

**SIGHUP 重读配置文件，只接受新增。** 实现在 `app/reload.zig`。

#### 为什么是信号而不是管理端口

1. **不新增任何网络暴露面。** 授权就是"谁能给这个进程发信号"，由操作系统按 uid 判定——
   而一个写错的管理端口认证就是一个远程后门。
2. **原样复用既有的解析与校验。** 走的还是 `foundation.config.load`，因此热加载自动继承
   全部启动期校验（域名重复、路由指向未登记 realm、`(realm, group, route_key)` 重复……）。
   另建一条命令通路等于把这些校验抄第二遍，两份迟早不一致。
3. **形态与现状连续**：运维本来就是"编辑 JSON + 重启"，现在只是去掉了重启。

用一条 `sigwait` 线程而不是信号处理函数：处理函数受异步信号安全约束（不能分配、不能加锁），
而重读配置两样都要。做法是在拉起任何线程之前屏蔽 SIGHUP（屏蔽字被后续线程继承），信号因此
只会停在进程级待决队列里，由专职线程取走——处理逻辑跑在一条普通线程上，什么都能做。

#### 两张表的并发形态

`foundation/realm.zig` 的 SNI 表与 `backend/catalog.zig` 的路由目录用同一套办法：
**定容 slab + 原子长度**。启动期按 `realm_capacity` / `route_capacity` 一次分配，运行期只填
后面的空位；已登记部分只读、永不移动、永不释放，所以正在扫表的读者不可能踩到搬迁或悬垂。
写者先填好槽位再用 release 序发布长度，读者用 acquire 序读长度——读到的长度所覆盖的内容
必定已经写完。**因此不需要锁、不需要 RCU、也不需要回收宽限期。**

代价是不支持删除，而删除也不该支持：一条还有在途交换的路由、一个还有连接的 realm，
都没有安全的移除时机。

#### 只接受新增

- **改**：改一个 realm 的 id 或域名，等于把现有连接的命名空间悄悄重新划分；改一条路由的
  endpoints，等于让在途交换的后半段发给另一个后端。
- **删**：判据是"表里有、文件里没有"，因此运维也不能靠删掉文件里的条目来清理。

两者都**整次拒绝**（全有或全无）：部分生效会让配置文件与进程状态处于一个谁都说不清的中间态。
热加载失败时两张表一个字节都没动，服务不受影响。

#### 新 realm 的路由怎么来

光有 SNI 映射没用——新 realm 的客户端能连上，但每次交换都 `route not found`、也无法认证。
所以路由声明也要能追加。但 transport 实例**必须在各自 Worker 的线程上创建**：它持有绑在
那条事件循环上的句柄（DNS 解析、重试定时器）与那个 Worker 私有的共享池引用。

分工因此是：**信号线程只往共享目录里追加声明，实例由第一个真正用到它的 Worker 在自己线程上
惰性创建**（`GatewayWorker.findTransport`，只在交换起点调用——中途查不到是异常，就地新建
只会把半条字节流发给一个全新的后端连接）。顺带的好处是没有那个 realm 流量的 Worker 不会
为它白付一个 socket 与若干后端连接。

启动期声明的路由照旧预建，行为与从前一致（第一次请求不必等 DNS 与握手）。

- **排空期没有定向重定向**。`worker.pollShutdown` 的行为是：广播 `left` → 停止接新连接 →
  等 `drain_timeout_us` → 到点直接停，日志写 "stopping with N connection(s) left"。也就是
  自然断的走掉，没走掉的被硬丢，客户端自己重连到 DNS/LB 给的任意节点。

  丢连接本身不是问题（客户端本来就要能重连），问题是这批连接的 home 在 `left` 之后已经
  变了，盲重连大概率还要再吃一次 `redirect`——两次往返；而且一批连接同时无引导地重连，
  落点由 LB 决定而不是由 HRW 决定，正是 §8.5 想避免的形态。

  **补它不能直接复用 `auth.redirectToHome`**（这一点最初被低估了，记在这里免得下次再踩）：
  那个函数在 `home.node_id == self.placement.self.node_id` 时直接返回 false，而排空的那
  一刻**本地 `placement.nodes` 快照里还有自己**——`beginDrain` 只是把 `left` 广播出去，
  本地视图要等下一轮 SWIM 收敛再经 `refreshPlacement` 抄进来。于是 HRW 会给约 1/N 的连接
  算出 home == self，这些连接会被拒绝重定向、照旧被丢。所以需要的是一个**能排除自己**的
  目标选择，而 `redirectToHome` 表达不了它。另外广播策略下根本没有 home 概念，还需要一条
  "挑任意其他活节点"的降级路径；`dest_id == 0`（尚未认证）的连接也无从重定向。

  `preferred_address`（`picoquic.h:344` 的 `picoquic_tp_prefered_address_t`、`:376` 挂在

  真正的理由是**它不是重新归位机制**：`preferred_address` 只在握手期生效一次、每个上下文
  一个地址，而且带不了 worker 级的定位信息。我们的 `redirect` 携带 `RedirectHint`
  （home 地址 + placement hint），能把客户端引导到**具体某个 Worker**，严格比它更强。
  至于真把状态搬过去：那要连 TLS 密钥、包号空间、ACK 状态、流控窗口、拥塞状态一起搬，
  换来的收益只是"省掉一次重连"。§8.5 的三道防线 + `redirect` 已经覆盖了这个需求，
