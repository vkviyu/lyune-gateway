# Lyune Gateway 协议设计文档

## 1. 协议概述

### 1.1 分层设计理念

Lyune Gateway 采用两层协议设计：

| 层级       | 名称                 | 职责                       | 处理方                |
| ---------- | -------------------- | -------------------------- | --------------------- |
| 帧协议层   | Frame Protocol       | 传输控制（怎么传、传给谁） | 网关 + 客户端 SDK     |
| 业务协议层 | Application Protocol | 业务语义（传什么）         | 后端服务 + 客户端 SDK |

**核心原则**：

- 网关**只解析帧头**，不关心 Body 内容
- Body 内部采用**类 HTTP 语义**，便于复用现有生态
- **全链路帧协议透传**：上下行均传输完整帧，保持上下文完整性

**上下行帧协议职责**：

| 方向                   | 网关行为                       | 后端需要理解   |
| ---------------------- | ------------------------------ | -------------- |
| **上行** (客户端→后端) | 解析帧头做路由，**转发完整帧** | **完整帧协议** |
| **下行** (后端→客户端) | 按帧头指示转发，**不修改帧**   | **完整帧协议** |

> **为什么全链路透传完整帧？**
>
> **全链路上下文完整性**：帧头不仅是网关控制指令，更是全链路上下文信息。
>
> | 字段          | 后端读取后的价值                           |
> | ------------- | ------------------------------------------ |
> | TransportMode | 知道客户端期望的响应方式，选择最佳处理策略 |
> | RouteKey      | 请求来源追踪，用于分布式监控和统计         |
> | Flags         | 知道数据是否压缩/加密，正确解析 Body       |
> | Seq           | 请求-响应关联，全链路追踪 ID               |

## 2. 帧协议（网关层）

### 2.1 帧头字段说明

| 字段        | 大小 | 说明                              |
| ----------- | ---- | --------------------------------- |
| Magic       | 2B   | 魔数 `0xFEFE`，用于快速识别有效帧 |
| Version     | 1B   | 协议版本，当前为 `3`              |
| Mode        | 1B   | 传输模式（TransportMode）         |
| RouteKey    | 1B   | 路由标识                          |
| Flags       | 1B   | 标志位                            |
| Reserved    | 2B   | 保留字段                          |
| Sequence    | 4B   | 序列号（大端序）                  |
| Body Length | 4B   | Body 长度（大端序）               |

### 2.2 TransportMode（传输模式）

编码规则：**高 4 位 = 传输路径，低 4 位 = 传输方式**

| 值   | 名称             | 路径 | 方式 | 说明                       |
| ---- | ---------------- | ---- | ---- | -------------------------- |
| 0x00 | relay_buffered   | 中继 | 缓冲 | 完整消息通过消息中间件转发 |
| 0x01 | relay_streaming  | 中继 | 流式 | 流式分片通过消息中间件转发 |
| 0x10 | direct_buffered  | 直连 | 缓冲 | 完整消息直连后端服务器转发 |
| 0x11 | direct_streaming | 直连 | 流式 | 流式分片直连后端服务器转发 |
| 0xFF | control          | -    | -    | 控制帧，网关本地处理       |

**传输路径**：

- **中继 (relay)**：消息通过 NATS 等消息中间件转发
- **直连 (direct)**：网关通过服务发现直接连接后端

**传输方式**：

- **缓冲 (buffered)**：完整接收后再转发
- **流式 (streaming)**：收到即转发，适合 AI 响应、音视频等

### 2.3 RouteKey（路由标识）

u8 类型，作为服务标识使用：

| 模式     | RouteKey 含义                        |
| -------- | ------------------------------------ |
| 直连模式 | 服务发现的 key，网关查询对应后端地址 |
| 中继模式 | 消息中间件的 topic/queue 标识        |
| 控制模式 | 复用为 ControlType（见下文）         |

具体值的业务含义由配置文件定义，例如：

- `0x01` → `ai-service`
- `0x02` → `im-service`
- `0x03` → `file-service`

### 2.4 Flags（标志位）

| Bit | 名称       | 说明                          |
| --- | ---------- | ----------------------------- |
| 0   | compressed | Body 是否压缩                 |
| 1   | encrypted  | Body 是否加密                 |
| 2   | need_ack   | 是否需要 ACK 确认             |
| 3   | sof        | 流式首包标志 (Start of Frame) |
| 4   | eof        | 流式末包标志 (End of Frame)   |
| 5-7 | reserved   | 保留                          |

### 2.5 ControlType（控制帧类型）

当 `TransportMode == control` 时，RouteKey 字段复用为 ControlType：

| 范围      | 类别       | 具体类型                                                |
| --------- | ---------- | ------------------------------------------------------- |
| 0x00-0x0F | 心跳类     | heartbeat, heartbeat_ack, ping, pong                    |
| 0x10-0x1F | 认证类     | auth_request, auth_success, auth_failure                |
| 0x20-0x2F | 连接控制类 | kick_off, disconnect, force_close                       |
| 0x30-0x3F | 会话类     | session_resume, session_resume_ack, session_resume_fail |
| 0xF0-0xFF | 系统类     | gateway_error, maintenance                              |

## 3. 业务协议（应用层）

### 3.1 设计原则

Body 内部采用**类 HTTP 语义**，便于：

1. 后端复用现有 HTTP 框架
2. 路径隐式表达业务类型
3. 头部表达数据特性（如 Content-Type）

### 3.2 Body 格式约定

```
┌─────────────────────────────────────────────────────────────┐
│                    Body 格式（类 HTTP）                      │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  请求格式:                                                   │
│  ┌─────────────────────────────────────────────────────┐   │
│  │ POST /v1/chat/completions HTTP/1.1                  │   │
│  │ Content-Type: application/json                      │   │
│  │ X-Request-Id: uuid-xxx                              │   │
│  │                                                     │   │
│  │ {"model":"gpt-4","messages":[...]}                  │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                             │
│  响应格式:                                                   │
│  ┌─────────────────────────────────────────────────────┐   │
│  │ HTTP/1.1 200 OK                                     │   │
│  │ Content-Type: text/event-stream                     │   │
│  │                                                     │   │
│  │ data: {"content":"Hello"}                           │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 3.3 常见 Content-Type

| Content-Type             | 说明          | 典型场景          |
| ------------------------ | ------------- | ----------------- |
| application/json         | JSON 数据     | 普通 RPC、IM 消息 |
| text/event-stream        | SSE 流式数据  | AI 流式响应       |
| application/octet-stream | 二进制数据    | 文件传输          |
| application/protobuf     | Protobuf 编码 | 高性能场景        |

## 4. 数据流转示例

### 4.1 上行流程（客户端 → 后端）

```
┌─────────────────────────────────────────────────────────────────┐
│                    上行数据流转                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  1. 客户端构造完整帧                                             │
│     ┌─────────────────────────────────────────────┐            │
│     │ Mode: direct_streaming (0x11)              │ ← 帧头      │
│     │ RouteKey: 0x01 (ai-service)                │            │
│     │ Flags: sof=true                            │            │
│     │ Seq: 1001                                  │            │
│     │ BodyLen: 128                               │            │
│     ├─────────────────────────────────────────────┤            │
│     │ POST /v1/chat/completions HTTP/1.1         │ ← Body     │
│     │ Content-Type: application/json              │            │
│     │                                             │            │
│     │ {"model":"gpt-4","messages":[...]}         │            │
│     └─────────────────────────────────────────────┘            │
│                         │                                       │
│                         ▼                                       │
│  2. 网关解析帧头做路由决策                                       │
│     - Mode = direct_streaming → 直连 + 流式                     │
│     - RouteKey = 0x01 → 查服务发现 → ai-service                 │
│     - 从连接池获取到 ai-service 的连接                           │
│                         │                                       │
│                         ▼                                       │
│  3. 网关转发完整帧给后端（保留全链路上下文）                      │
│     ┌─────────────────────────────────────────────┐            │
│     │ Mode: direct_streaming (0x11)              │ ← 帧头     │
│     │ RouteKey: 0x01 (ai-service)                │ (原样保留) │
│     │ Flags: sof=true                            │            │
│     │ Seq: 1001                                  │            │
│     │ BodyLen: 128                               │            │
│     ├─────────────────────────────────────────────┤            │
│     │ POST /v1/chat/completions HTTP/1.1         │ ← Body     │
│     │ Content-Type: application/json              │            │
│     │                                             │            │
│     │ {"model":"gpt-4","messages":[...]}         │            │
│     └─────────────────────────────────────────────┘            │
│                         │                                       │
│                         ▼                                       │
│  4. 后端解析帧头获取上下文，处理 Body                            │
│     - 读取 Mode: 知道客户端期望流式响应                          │
│     - 读取 Seq: 用于请求-响应关联                                │
│     - 处理 Body 业务数据                                         │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 4.2 下行流程（后端 → 客户端）

```
┌─────────────────────────────────────────────────────────────────┐
│                    下行数据流转                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  1. 后端构造完整帧（包含帧头）                                    │
│     ┌─────────────────────────────────────────────┐            │
│     │ Mode: direct_streaming (0x11)              │ ← 帧头      │
│     │ RouteKey: 0x01 (ai-service)                │ (后端构造) │
│     │ Flags: eof=false                           │            │
│     │ Seq: 2001                                  │            │
│     │ BodyLen: 32                                │            │
│     ├─────────────────────────────────────────────┤            │
│     │ data: {"content":"Hello"}                  │ ← Body     │
│     └─────────────────────────────────────────────┘            │
│                         │                                       │
│                         ▼                                       │
│  2. 网关收到完整帧                                               │
│     - 解析帧头获取 Mode 和 RouteKey                              │
│     - 根据 Mode 确定传输方式 (streaming)                         │
│     - 根据 RouteKey 找到对应的客户端连接                          │
│                         │                                       │
│                         ▼                                       │
│  3. 网关直接转发完整帧给客户端（不修改）                          │
│     ┌─────────────────────────────────────────────┐            │
│     │ Mode: direct_streaming (0x11)              │ ← 帧头      │
│     │ RouteKey: 0x01                             │            │
│     │ Flags: eof=false                           │            │
│     │ Seq: 2001                                  │            │
│     ├─────────────────────────────────────────────┤            │
│     │ data: {"content":"Hello"}                  │ ← Body     │
│     └─────────────────────────────────────────────┘            │
│                         │                                       │
│                         ▼                                       │
│  4. 客户端解析帧头和 Body                                        │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**关键点**：

- 后端必须理解帧协议，才能构造正确的帧头
- 后端通过帧头控制网关的传输行为（Mode、Flags）
- 网关只做转发，不修改帧内容

## 5. 错误处理约定

### 5.1 网关层错误

通过控制帧 `ControlType.gateway_error` 返回：

| 错误场景     | 处理方式                                  |
| ------------ | ----------------------------------------- |
| 帧头解析失败 | 返回 gateway_error，Body 携带错误码和描述 |
| 服务不可达   | 返回 gateway_error，错误码指示服务不可用  |
| 认证失败     | 返回 auth_failure 控制帧                  |

### 5.2 业务层错误

通过 Body 内的 HTTP 状态码返回：

```
HTTP/1.1 500 Internal Server Error
Content-Type: application/json

{"error": "service unavailable", "code": 50001}
```

### 5.3 错误码分区

| 范围 | 层级   | 说明       |
| ---- | ------ | ---------- |
| 1xxx | 网关层 | 帧协议错误 |
| 2xxx | 网关层 | 路由错误   |
| 3xxx | 网关层 | 连接错误   |
| 4xxx | 业务层 | 客户端错误 |
| 5xxx | 业务层 | 服务端错误 |

## 6. 参考实现

帧协议的 Zig 实现见以下源文件：

### 帧格式定义 — `src/protocol/frame.zig`

- `TransportMode` 枚举及辅助方法（`isRelay`/`isDirect`/`isStreaming` 等）
- `ControlType` 枚举及分类判断（`isHeartbeat`/`isAuth`/`isSession` 等）
- `FrameHeader` 结构体及大端序编解码（`encode`/`decode`）
- `Flags` 标志位定义

### 编解码器 — `src/protocol/codec.zig`

- `FrameEncoder`：构建完整帧（帧头 + Body），提供通用 `encode` 方法和控制帧快捷方法（`heartbeat`/`auth`/`kickOff` 等）
- `FrameDecoder`：增量解码器，使用状态机（`reading_header` → `reading_body`）处理 QUIC 流上的粘包拆包，最大帧限制 16MB

### 流处理器 — `src/protocol/handler.zig`

- `StreamHandler`：类型擦除的统一流处理接口（vtable 模式），支持 `onData`/`deinit` 操作
- `BufferedMessageHandler`：累积所有数据直到 QUIC Stream FIN，然后回调完整消息。适用于普通请求-响应场景
- `StreamingMessageHandler`：收到数据即透传回调，适用于 AI 流式响应、音视频等低延迟场景
- `StreamDelegate(ContextType)`：泛型委托，提供类型安全的回调桥接
