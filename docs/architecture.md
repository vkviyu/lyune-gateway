# Lyune Gateway 架构设计文档

## 1. 系统概述

Lyune Gateway 是一个基于 QUIC 协议的高性能网关，专为实时通信场景设计。

### 1.1 核心定位

- **传输层网关**：只关心"数据怎么传、传给谁"，不关心"传什么"
- **协议解耦**：网关层帧协议与业务层应用协议分离
- **双模传输**：同时支持中继（通过消息中间件）和直连（服务发现直连）两种模式

### 1.2 核心能力

| 能力       | 说明                                                                             |
| ---------- | -------------------------------------------------------------------------------- |
| 多模式传输 | 缓冲传输（完整消息）、流式传输（分片实时转发）                                   |
| 灵活路由   | 中继模式走消息中间件，直连模式走服务发现                                         |
| 连接管理   | QUIC 连接复用、会话管理、连接迁移                                                |
| 高性能     | 基于 Zig + libxev (macOS kqueue / Linux io_uring) 异步 I/O，Thread-per-Core 架构 |

## 3. 运行时架构

### 3.1 Thread-per-Core 模型

网关采用 Thread-per-Core 架构，每个线程拥有完全独立的资源，线程间无共享状态、无锁竞争：

```
┌─────────────────────────────────────────────────────────────────┐
│                    Thread-per-Core 模型                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  ┌─────────────────┐  ┌─────────────────┐     ┌──────────────┐ │
│  │   Thread 0      │  │   Thread 1      │ ... │  Thread N-1  │ │
│  │  ┌───────────┐  │  │  ┌───────────┐  │     │ ┌──────────┐ │ │
│  │  │ xev.Loop  │  │  │  │ xev.Loop  │  │     │ │ xev.Loop │ │ │
│  │  ├───────────┤  │  │  ├───────────┤  │     │ ├──────────┤ │ │
│  │  │ServerDriver│  │  │  │ServerDriver│  │     │ │ServerDrv │ │ │
│  │  │  ┌──────┐ │  │  │  │  ┌──────┐ │  │     │ │ ┌──────┐ │ │ │
│  │  │  │Endpt │ │  │  │  │  │Endpt │ │  │     │ │ │Endpt │ │ │ │
│  │  │  ├──────┤ │  │  │  │  ├──────┤ │  │     │ │ ├──────┤ │ │ │
│  │  │  │IoLoop│ │  │  │  │  │IoLoop│ │  │     │ │ │IoLoop│ │ │ │
│  │  │  └──────┘ │  │  │  │  └──────┘ │  │     │ │ └──────┘ │ │ │
│  │  ├───────────┤  │  │  ├───────────┤  │     │ ├──────────┤ │ │
│  │  │ConnManager│  │  │  │ConnManager│  │     │ │ConnMgr   │ │ │
│  │  └───────────┘  │  │  └───────────┘  │     │ └──────────┘ │ │
│  └────────┬────────┘  └────────┬────────┘     └──────┬───────┘ │
│           │                    │                      │         │
│           └────────────┬───────┘──────────────────────┘         │
│                        │                                        │
│                 SO_REUSEPORT                                    │
│              ┌─────────┴─────────┐                              │
│              │   UDP Port 4433   │                              │
│              └───────────────────┘                              │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

- 所有线程通过 `SO_REUSEPORT` 绑定同一 UDP 端口，由内核分发入站包
- 每个线程的 `ConnectionManager` 是线程本地的，无需互斥锁
- 线程数默认等于 CPU 核心数，可通过 `--threads N` 指定

### 3.2 三层驱动结构

每个线程内部的处理分为三层：

```
┌──────────────────────────────────────────────────────┐
│                  GatewayWorker (业务层)                │
│  职责：连接管理、流分发、消息聚合                       │
│  组件：ConnectionManager, BufferedMessageHandler       │
├──────────────────────────────────────────────────────┤
│                  ServerDriver (驱动层)                 │
│  职责：组装 Endpoint + IoLoop，驱动事件循环             │
│  核心：收包 → 协议处理 → 发包 → 定时器更新              │
│  发送：GSO 缓冲区 64KB，批量最多 64 包                  │
├──────────────────────────────────────────────────────┤
│                  IoLoop (传输层)                       │
│  职责：基于 libxev 的 UDP 收发、定时器、异步通知        │
│  平台：macOS kqueue / Linux io_uring                   │
│  优化：Linux sendmmsg 批量发送                          │
└──────────────────────────────────────────────────────┘
```

事件驱动流程：

```
UDP 包到达
  → IoLoop.recvCallback (libxev kqueue/io_uring 事件)
    → ServerDriver.internalOnUdpRecv
      → Endpoint.handleIncomingPacket (picoquic 协议栈处理)
      → ServerDriver.processQuicEvents
        → flushPendingPackets (批量发包)
        → updateTimer (调度下一次唤醒)
      → 回调 GatewayWorker.handleNewConnection / handleStreamData / handleConnectionClose
```

### 3.3 Connection ID 线程路由

picoquic 的 Connection ID 回调中，CID 的第一个字节编码了线程 ID：

```
Connection ID 格式：
┌──────────┬──────────────────────┐
│ thread_id│   random bytes       │
│  (1 byte)│   (7 bytes)          │
└──────────┴──────────────────────┘
```

这使得内核通过 `SO_REUSEPORT` 分发包后，每个线程能快速判断该包是否属于自己管理的连接，实现无锁负载均衡。

## 4. 协议分层模型

### 4.1 分层架构

```
┌─────────────────────────────────────────────────────────────────┐
│                        协议分层                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │              业务协议层 (Application Protocol)           │   │
│  │  • 类 HTTP 语义 (请求行/状态行 + 头部 + 数据)            │   │
│  │  • 由后端服务和客户端 SDK 处理                           │   │
│  └─────────────────────────────────────────────────────────┘   │
│                            ▲                                    │
│                            │ Body                               │
│                            │                                    │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │              帧协议层 (Frame Protocol)                   │   │
│  │  • 16 字节帧头 + 变长 Body                               │   │
│  │  • 由网关和客户端 SDK 处理                               │   │
│  └─────────────────────────────────────────────────────────┘   │
│                            ▲                                    │
│                            │                                    │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │              传输层 (QUIC)                               │   │
│  │  • 多路复用、0-RTT、连接迁移                             │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 4.2 各端职责划分

| 角色         | 解析协议层        | 核心职责                            |
| ------------ | ----------------- | ----------------------------------- |
| **客户端**   | 帧协议 + 业务协议 | 封装/解析完整帧，构造/处理业务负载  |
| **网关**     | 仅帧协议          | 解析帧头做路由决策，**不解析 Body** |
| **后端服务** | 仅业务协议        | **不理解帧头**，只处理业务负载      |

### 4.3 设计优势

1. **职责清晰**：网关专注传输路由，后端专注业务逻辑
2. **解耦彻底**：后端无需理解网关协议，可独立开发部署
3. **复用性高**：后端可复用现有 HTTP 框架和生态
4. **扩展灵活**：新增服务只需配置 RouteKey 映射

## 5. 连接管理策略

### 5.1 Gateway-initiated 模式

采用**网关主动连接后端**的模式：

```
┌────────────────────────────────────────────────────────────────┐
│                     连接管理流程                                │
├────────────────────────────────────────────────────────────────┤
│                                                                │
│   网关启动                                                      │
│      │                                                         │
│      ▼                                                         │
│   订阅服务发现 (etcd/Consul)                                    │
│      │                                                         │
│      ▼                                                         │
│   ┌─────────────────────────────────────────┐                  │
│   │ RouteKey 映射表                          │                  │
│   │ ┌─────────────────────────────────────┐ │                  │
│   │ │ 0x01 → ai-service    → [实例列表]  │ │                  │
│   │ │ 0x02 → im-service    → [实例列表]  │ │                  │
│   │ │ 0x03 → file-service  → [实例列表]  │ │                  │
│   │ └─────────────────────────────────────┘ │                  │
│   └─────────────────────────────────────────┘                  │
│      │                                                         │
│      ▼                                                         │
│   收到客户端请求                                                │
│      │                                                         │
│      ├─── 解析帧头，获取 TransportMode 和 RouteKey              │
│      │                                                         │
│      ├─── 直连模式 (direct_*)                                  │
│      │       │                                                 │
│      │       ▼                                                 │
│      │    查询 RouteKey 对应的服务实例                          │
│      │       │                                                 │
│      │       ▼                                                 │
│      │    从连接池获取/新建 QUIC 连接                           │
│      │       │                                                 │
│      │       ▼                                                 │
│      │    剥离帧头，转发 Body                                   │
│      │                                                         │
│      └─── 中继模式 (relay_*)                                   │
│              │                                                 │
│              ▼                                                 │
│           发送到 NATS 对应 topic (RouteKey 作为 topic 标识)     │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

## 6. 扩展性设计

### 6.1 新增后端服务

只需两步：

1. 在服务发现中注册新服务
2. 配置 RouteKey 到服务名的映射

**网关代码无需修改。**

### 6.2 TransportMode 扩展

当前编码规则：高 4 位表示路径，低 4 位表示方式

| 路径         | 方式                     | 预留空间               |
| ------------ | ------------------------ | ---------------------- |
| 0x0\_ (中继) | 0x_0 (缓冲), 0x_1 (流式) | 0x02-0x0F 可扩展新方式 |
| 0x1\_ (直连) | 0x_0 (缓冲), 0x_1 (流式) | 0x12-0x1F 可扩展新方式 |
| 0x2*-0xE*    | -                        | 预留新路径类型         |
| 0xF\_ (控制) | -                        | 控制帧专用             |

### 6.3 RouteKey 空间

u8 类型，支持 256 种服务标识，对绝大多数系统足够。
